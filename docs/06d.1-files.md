# Step 6d.1: modules in files of their own

Code: `src/load.rs` (which file each `mod m;` is, and reading them),
`src/source.rs` (the files laid end to end, and which one an offset is in),
and, for the tools, `src/lsp.rs` (which program an open file is in).

A program of several files starts in `main.t`. `mod geo;` there is the
module `geo`, whose items are in `geo.t` next to it:

```text
shop/
├── main.t          mod geo;  mod inner { pub mod deep; }  fn main() { .. }
├── geo.t           pub mod area;  pub struct Point { .. }
├── geo/
│   └── area.t      use super::Point;  pub fn of(p: &Point) -> int { .. }
└── inner/
    └── deep.t      pub fn answer() -> int { 42 }
```

The file of `geo.t`'s `mod area;` is `geo/area.t`:

```rust
use super::Point;

pub fn of(p: &Point) -> int { p.x * p.y }
```

It's hermetic, as every module is (see
[docs/06d-modules.md](06d-modules.md)): `Point` is `super::Point`, not just
`Point`, because nothing of the modules around a module is in scope in it.

## Where a module's file is

The file of the module `a::b` is `a/b.t`, from the directory `main.t` is
in. That's the only place it can be: there's no `a/b/mod.t`, and no
attribute to point a module elsewhere. A `mod b;` inside `mod a { .. }`
written inline is `a/b.t` too, so `inner::deep` above is `inner/deep.t`.

**Lemma F2 (files follow from paths).** A module's file depends only on its
path. Module paths are unique, so no two modules read the same file, and a
program's files are finite, so reading them ends. The one way round that is
a link, like a directory `a` linking back to the one it's in, which would
make `a/a/a/..` go on forever, so a file already read, through a link or
not, is an error.

`main.t` is reserved for where a program starts: a `mod m;` in a program
that starts in a file called anything else is an error, and so is a module
in a file called `main`:

```rust,error
mod m;
// error: only a program that starts in `main.t` can have
```

So a file's program is the nearest `main.t` above it that has it. The
editor support needs that: it's given one file, and has to find the rest.

## A file means what braces would

**Lemma F1 (a file is braces).** `mod m;` means just what
`mod m { .. }` would with `m.t`'s items between the braces.

Proof sketch: the loader parses `m.t` into the module `mod m;` made, as if
its items were written there, and nothing after that knows a module came
from a file. What the items mean can't depend on where they're written,
because modules are hermetic (6d): a module sees its own items, its `use`s
and the prelude, wherever it is.

So no rule of 6d changes, and neither does anything after parsing.
`load.rs` has a test that a program of files and the same program inline
monomorphise to the same items.

## Which file an offset is in

**Lemma F3 (one text).** The files are laid end to end in one text, with a
newline between each two, and a `Span` is still a range in it. Each file
is lexed on its own and its tokens moved to where it starts, so no token,
and no span, crosses from one file into another. The newline between them
means the end of a file is never the start of the next, so an edit that
inserts at the end of a file, like a missing `}`, is in the file it should
be.

Every phase works on spans as before. Only messages and the tools ask
which file an offset is in: an error in `geo/area.t` says
`--> shop/geo/area.t:3:5`, a fix or a rename edits each file it touches,
and an `#[allow(..)]` on `mod m;` turns its lints off in `m.t` and in the
files of the modules in it.

## Tools

- `t run`, `t check` and `t mono` read a program's files from beside its
  `main.t`.
- `t fmt` formats the files it's given, each on its own; it doesn't follow
  `mod m;`.
- `t lsp` checks an open file as part of its program, with what the editor
  has for the files that are open and what's on disk for the others.
  Diagnostics go to the file they're in; going to a definition, finding
  references and renaming cross files, and going to the definition of `m`
  in `mod m;` opens `m.t`.

## Design decisions worth noticing

- **One place per module.** A module could be in `a/b.t` or `a/b/mod.t` in
  Rust 2018, or anywhere with `#[path]`. Here a path names one file, so
  there's nothing to look up and nothing ambiguous.
- **`main.t` is where a program starts.** Without a manifest, something has
  to say which file is the root. A name is the simplest thing that makes a
  file's program a function of where the file is. A library's root will be
  `lib.t`, when there are libraries.
- **Spans stay offsets.** A file in each `Span` would touch every phase, and
  `Span::to` would have to refuse two files. One text with a map of where
  each file is touches only what shows a span to a person.

## Exercises

1. Move a module of one of your programs into a file of its own. What
   changes, and what doesn't?
2. Why would a module that could see the names around it (not hermetic)
   break lemma F1? Write two programs that would mean different things.
3. Delete the newline `Sources::add` puts between files and run the tests.
   Which fails, and what would go wrong for someone using the editor?
4. Why can't a module in a file be called `main`, even inside another
   module? What would the editor have to guess if it could?
