# Step 6a.1: linear types

Code: `src/traits.rs` (which types are `Discard`), `src/check/traits.rs`
(deriving it, and `Copy` needing it), `src/borrowck/build.rs` (patterns
that use values up), `src/borrowck/moves.rs` (`linear`, the check) and
`src/check.rs` (`replace` and `swap`).

```rust
struct Fd { n: int }

fn open(n: int) -> Fd { Fd { n } }

// Taking it apart, by value, uses it up.
fn close(fd: Fd) -> int {
    let Fd { n } = fd;
    n
}

fn main() {
    let fd = open(3);
    print(close(fd)); // expect: 3
}
```

`Fd` stands for a file descriptor, a thing that has to be closed. Leave out
the `close` and the program doesn't compile:

```rust,error
struct Fd { n: int }

fn open(n: int) -> Fd { Fd { n } }

fn main() {
    let _fd = open(3);
}
// error: `_fd` is never used up, and its type, `Fd`, isn't `Discard`
```

Since step 5, a value that isn't `Copy` can be used at most once: after it's
moved, it's gone. Now it must be used *exactly* once, unless its type says
it may be thrown away, with `#[derive(Discard)]`. The values of plain data
can be, so most structs and enums say so; a resource doesn't, and then
forgetting to close it is a compile error rather than a leak.

## Using a value up

A value is used up when it's moved somewhere, into a function, a variable,
a struct, a box, or out as a result, or when a pattern takes it apart by
value. It's *thrown away* when:

- the variable holding it goes out of scope, at the end of its block, or
  by `return`, `break` or `continue`, or when a function returns, for a
  parameter;
- it's a temporary nothing moves out of: `open(1);` on its own, or
  `let _ = open(1);`, as `_` binds nothing;
- its place gets a new value: `fd = open(2)` throws the old one away, as
  does `*r = open(2)` through a `&mut`.

Each of those is an error if what's thrown away, or any part of it still
there, isn't `Discard`. A struct whose fields have all been moved out has
nothing left to throw away, so moving its parts out uses it up, as taking
it apart does. A part that's gone can be given a new value, and then that
must be used up too.

A leading `_` doesn't help: `_fd` must be used up too. So the warning for an
unused `fd` says to use it up, rather than offering to rename it.

A path that never goes on is exempt. After a call that returns `!`
nothing is dropped, so a function can give up while holding a resource:

```rust
struct Fd { n: int }

fn close(fd: Fd) -> int {
    let Fd { n } = fd;
    n
}

fn die() -> ! {
    loop {}
}

fn checked(n: int, fd: Fd) -> int {
    if n < 0 {
        die();
    }
    close(fd)
}

fn main() {
    print(checked(1, Fd { n: 2 })); // expect: 2
}
```

T has no unwinding: a panic, when there are panics, aborts the program,
which hands everything back to the system at once. So the promise linear
types make is about every path that *goes on*: on each of them, every
value is used up. Unwinding would break it, as it runs the drops on the
way out, which here is throwing values away.

## Weakening and contraction

A typing context Γ lists the variables in scope. Two rules of ordinary type
systems say what can be done with them, though they're usually left
unsaid (`moves.rs` has them):

```text
  Γ ⊢ e : U                         Γ, x : T, x : T ⊢ e : U
 ------------------ (Weaken)       ------------------------- (Contract)
  Γ, x : T ⊢ e : U                  Γ, x : T ⊢ e : U
```

*Weakening*: a variable needn't be used. *Contraction*: it can be used
twice. Take one or both away and the type system is *substructural*
(Walker, 2005):

| Rules | System | A variable is used | In T |
|---|---|---|---|
| both | unrestricted | any number of times | `Copy` (so `Discard`) |
| weakening | affine | at most once | `Discard`, not `Copy` |
| neither | linear | exactly once | neither |
| contraction | relevant | at least once | not allowed |

Step 5 kept weakening for every type, so moves made T affine, as Rust is.
Now weakening holds only for `Discard` types, and contraction only for
`Copy` ones. Under Curry–Howard, a linear variable is a resource in Girard's
linear logic: a proof that consumes `A` to give `B` can't also keep `A`, or
make it vanish.

`trait Copy: Discard` rules the last row out: a value that's copied has
copies, and each would need using up, which isn't a promise anyone can
check. Relevant types could come later, by dropping the supertrait, though
then `T: Copy` would no longer give `T: Discard`.

## `Discard`

`Discard` is a trait with no methods, like `Copy`, and it's built in:

- `int`, `bool`, `()`, `!` and functions are `Discard`;
- so are references, `&T` and `&mut T`, whatever `T` is: dropping a
  reference doesn't drop what it points to;
- `Box<T>` is `Discard` if `T` is. A `Box<Fd>` is used up by using up
  `*b`, which frees the box;
- a struct or enum is if it says so, with `#[derive(Discard)]`, or with
  `impl Discard for P {}`, which needs every field `Discard`. A derived
  impl needs of the type's parameters only what its fields do, as derived
  `Copy` and `Eq` do (docs/06-traits.md).

It's never assumed. Rust's auto traits (`Send`, `Sync`) hold for a type
unless it opts out, which would be the other way to do it, but here
forgetting the opt-out would let a resource leak silently, and a private
field of a library's type would decide whether users may throw its values
away. Forgetting `#[derive(Discard)]` is a compile error that says what to
add. Every struct and enum before this step got one.

```rust,error
#[derive(Copy)]
struct Point { x: int, y: int }

fn main() {}
// error: `Point` can't be `Copy` unless it's `Discard`
```

The error's fix makes it `#[derive(Discard, Copy)]`.

## Patterns use values up

Matching a value that isn't `Discard` by value against a struct or variant
pattern takes it apart, which uses it up, in every arm: `None` too, though
it has nothing in it. The pattern's variables get what they bind; anything
else in it, under a `_` or a `..`, is thrown away, so it must be
`Discard`. The value is gone after the match.

```rust
struct Fd { n: int }

fn close(fd: Fd) -> int {
    let Fd { n } = fd;
    n
}

#[derive(Discard)]
enum Option<T> { Some(T), None }

fn close_any(o: Option<Fd>) -> int {
    match o {
        Option::Some(fd) => close(fd),
        Option::None => 0,
    }
}

fn main() {
    print(close_any(Option::Some(Fd { n: 1 })) + close_any(Option::None)); // expect: 1
}
```

`Fd { n }` only copies an `int` out, but it still uses `fd` up: otherwise
a function could read the number and leave the `Fd` to be closed again. A
`_` arm doesn't take the value apart, so `match o { Option::Some(fd) =>
close(fd), _ => 0 }` leaves `o` unused in the second arm, and that's an
error. Matching through a reference only looks: `match &fd { Fd { n } =>
.. }` uses nothing up, and `fd` is still there after.

In MIR that's a statement of its own, `Consume(place, variant)`, after the
pattern's bindings (`build.rs`, `bind`).

## `replace` and `swap`

Through a `&mut`, a value can't be moved out, and giving it a new one would
throw the old one away. The built-in `replace(&mut x, v)` does both at
once: it puts `v` in `x` and gives back what was there.

```rust
struct Fd { n: int }

fn close(fd: Fd) -> int {
    let Fd { n } = fd;
    n
}

fn reopen(slot: &mut Fd, n: int) -> int { close(replace(slot, Fd { n })) }

fn main() {
    let mut fd = Fd { n: 1 };
    print(reopen(&mut fd, 2)); // expect: 1
    print(close(fd));          // expect: 2
}
```

Its type is `fn<'a, T>(&'a mut T, T) -> T`, for any `T`, as nothing is
thrown away. `swap(&mut a, &mut b)` exchanges two values, and is the more
basic of the two: `replace` can be written with it, by swapping `v` into
the place and returning it, but not the other way round, as `swap<T>` has
no `T` of its own to put in. Both are built in for now, as there are no
libraries to put them in.

## Generic code

A `T` may be anything, so it can't be thrown away unless a bound says it
may:

```rust,error
fn forget<T>(_x: T) {}

fn main() {
    forget(1);
}
// error: `_x` is never used up, and its type, `T`, isn't `Discard`; to let it be thrown away, add a bound: `T: Discard`
```

`fn forget<T: Discard>(_x: T) {}` is fine, and then `forget(fd)` isn't, as
`Fd` isn't `Discard`. A bound `T: Copy` gives `T: Discard`, as a supertrait
does. A default method that drops its `self` needs `Discard` as a
supertrait of its trait: `trait Ord: Eq + Discard`.

The check runs before monomorphisation, on generic code, like the rest of
the borrow checker: whether `T: Discard` holds is what the bounds say, not
what a caller picks.

## How it's checked

Whether a value has been used up depends on the path taken to get to where
it's dropped, so it's a dataflow problem over MIR, like moves (`moves.rs`).
But the two ask opposite questions:

- *Moves*: may it have been moved, on *some* path? Then it can't be used.
  Where paths meet, the moved places are what *either* brings: a union.
- *Linearity*: has it been used up, on *every* path? Only then can it be
  dropped without throwing anything away. Where paths meet, what's gone is
  what *both* bring: an intersection (`meet`).

Each is the conservative answer for its own rule. A place is gone if it,
or something it's part of, is, so the intersection of "`p` is gone" and
"`p.a` is gone" is "`p.a` is gone". Each drop then asks what's left
(`leftover`): nothing, if it's gone; nothing, if its type is `Discard`;
and if it's been partly moved out of or taken apart, whatever is left of
each part.

The check doesn't follow what conditions say: after `if c { fd = open(1);
}`, `fd` is used up on one path and not the other, and a second `if c {
close(fd) }` doesn't change that, as nothing links the two. The link can
be put in a value instead, which `match` then makes both cases of:

```rust,fragment
let o = if c { Option::Some(open(1)) } else { Option::None };
match o {
    Option::Some(fd) => close(fd),
    Option::None => 0,
}
```

Rust accepts the two `if`s, for its affine values, with a *drop flag*: a
`bool` at run time saying whether there's something left to drop. A
linear promise is made at compile time, so a flag can't keep it.

The paths that never go on are exempt with no extra rule: a call that
returns `!` ends its MIR block with no successor, so nothing after it is
in the graph, and neither are the drops that would have come later.

The interpreter checks the promise as it runs, as it does memory's
(docs/05-ownership.md): it knows from monomorphisation's copies which
types are `Copy` and which `Discard`, moves every value whose type isn't
`Copy`, uses up a value a pattern takes apart, and stops with "type
soundness violated" where a value that isn't `Discard` is thrown away
whole. Not on the way out of a run-time error, though: that's a panic,
which aborts, so nothing is really dropped.

## Design decisions worth noticing

- **Linear by default, `Discard` to opt out.** Plain data says it may be
  thrown away; a resource says nothing. Forgetting either way is caught:
  one is a compile error, and the other is never wrong, only strict.
- **No `mem::forget`.** A function that takes a `T` and throws it away
  needs `T: Discard`, so there's no way to leak a linear value. `assert`
  will borrow what it checks, as `==` does, rather than consume it.
- **Panics abort.** Only paths that go on need their values used up.
  Catching panics would need step 7's effects: a function that may panic
  couldn't be called while holding a linear value.
- **References are always `Discard`.** Throwing away a borrow gives the
  value back to its owner, who still has to use it up.
- **`Copy` needs `Discard`**, so there are no relevant types.
- **Moving every field out uses a struct up.** It's the same as taking it
  apart with a pattern; once there are modules, both will need the fields
  to be visible.

## Exercises

1. Write a program that uses its `Fd` up on every run but is rejected:
   two `if c` with the same `c`, one opening, one closing. Why can't a
   check that ignores the values of conditions accept it? What would?
2. Make `Consume` happen only when a pattern moves something out of the
   value (`build.rs`, `consumes_at`). Why can't `close` be written then?
   What could still destroy an `Fd`?
3. Write `replace` with `swap`. Then try to write `swap<T>` with `replace`,
   and say why it can't be done.
4. Try to write `forget<T>(_x: T)` in T. Then: a reference-counted pointer
   `Rc<T>` lets a value point to itself. Show how a cycle would leak a
   linear value, and what bound `Rc::new` would need.
5. Sketch unwinding: a panic in `checked` above, while `fd` is live. What
   would it have to do with `fd`, and why does that need either a
   destructor or a rule that `checked` can't panic?
6. Remove `trait Copy: Discard`. Which tests break, and what would
   `#[derive(Copy)] struct Ticket { n: int }` mean then?
7. A destructor: let `Discard` have a provided method `fn discard(self)`,
   and call it wherever a `Discard` value is dropped. Where in MIR would the
   calls go, and in what order for a struct's fields?
