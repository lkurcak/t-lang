# Step 6c.1: returning closures, opaque types

Code: `src/check/opaque.rs` (`Checker::opaque`, `Checker::hide` and
`Checker::opaque_cycles`), `src/traits.rs` (`OpaqueDef`, and what an opaque
type implements and normalises to), `src/borrowck.rs`
(`member_constraints`: which lifetimes the type behind one borrows for),
`src/borrowck/regions.rs` (variance and outlives) and `src/mono.rs`
(`Projections::reveal`).

```rust
fn adder(n: i64) -> impl Fn(i64) -> i64 with panic + Discard { move |x| x + n }

fn counter() -> impl FnMut() -> i64 with panic + Discard {
    let mut n = 0;
    move || {
        n += 1;
        n
    }
}

fn main() with panic {
    let add5 = adder(5);
    print(add5(1)); // expect: 6
    let mut next = counter();
    next();
    print(next()); // expect: 2
}
```

A closure that captures has a type of its own, which nothing can name
(docs/06c-closures.md), so until now no signature could say a function
returns one. `impl Fn(i64) -> i64 with panic` in a return type says it now: the
function returns *some* type that implements `Fn(i64) -> i64`, which it
picks, and that's all its callers know of it.

## Some type that does this

`impl Fn(i64) -> i64 with panic + Discard` is an *existential* type: ∃T. T: Fn(i64) ->
i64 + Discard, "there is a type `T` such that ...". The function picks the
`T`, its *hidden* type, and callers get a value of it without being told
which it is. That's how abstract types work in type theory (Mitchell and
Plotkin, *Abstract types have existential type*): a module that hides its
representation is a value of an existential type, and code using it can only
do what the interface says, so the representation can change without
breaking it.

Here the interface is the bounds. A caller can call the result of `adder`,
drop it, and pass it to anything that takes an `F: Fn(i64) -> i64`, and
nothing else, not even what the closure's type would allow:

```rust,error
trait Show {
    fn show(&self) -> i64;
}

impl Show for i64 {
    fn show(&self) -> i64 { *self }
}

fn one() -> impl Show + Discard { 1i64 }

fn main() {
    print(one() + 1); // error: `+` works on integers, not on `impl Show + Discard`
}
```

Outside the function, an opaque type is like a type parameter whose bounds
are what follows `impl` (`traits::OpaqueDef`). It implements what they say,
and what a blanket impl, `impl<T: Show> Twice for T`, gives anything that
does, and nothing else: an impl for the hidden type, `impl Tr for i64`,
doesn't apply. That's what makes it safe to replace it by the hidden type
afterwards: by coherence, a blanket impl that applies to it is the only
impl of its trait there is, so it's the one found for the hidden type too
(`opaque_traits.t`).

Each `impl` written is a type of its own. Two calls of `adder` return the
same type, at the same lifetimes, so both values can be stored in one
variable; two functions with the same return type written out don't:

```rust,error
fn a() -> impl Fn() -> i64 with panic + Discard { || 1 }

fn b() -> impl Fn() -> i64 with panic + Discard { || 2 }

fn main() {
    let f = if true { a() } else { b() }; // error: each `impl` type is a type of its own
    print(f());
}
```

An `impl` can be anywhere in a return type, as in `-> Option<impl Fn()>`,
of a function, a nested one, or a method of an inherent impl. It can't be in
a parameter's type, where a type parameter does the job, nor a function
type, nor a trait's methods, where each impl would pick its own: that's an
associated type.

## Inside the function

In its own body, a function's opaque type is the type its body returns, to
be inferred, which must have what the bounds say (`Checker::hide`). Those
bounds are known while the body is checked, so a closure returned for `impl
Fn(i64) -> i64` is checked as one taking an `i64`, as it would be when passed
to a function wanting an `F: Fn(i64) -> i64`. The bounds must hold of the
hidden type with the function's own bounds:

```rust,error
struct Fd { n: i64 }

fn close(fd: Fd) -> i64 {
    let Fd { n } = fd;
    n
}

fn once(fd: Fd) -> impl Fn() -> i64 with panic {
    // error: this closure is only `FnOnce`, as it moves `fd` out
    move || close(fd)
}

fn main() {
    print(once(Fd { n: 1 })());
}
```

Callers only ever see the bounds, so checking one doesn't need the body of
the function it calls, and the functions can be checked in any order. A
function can even call itself, getting its own opaque type, as long as the
hidden type doesn't hold it. One that did would be a type that holds itself,
which no finite type is, so that's rejected, through other functions'
opaque types too (`Checker::opaque_cycles`, `err_opaque_cycle.t`).

## What it borrows

A closure that captures by reference holds references, and so may the
hidden type behind an `impl`. Which lifetimes may it borrow for? Any of the
function's, elided ones included, and `'static`: an opaque type is generic
over every lifetime and type parameter of the function, as Rust's are since
its 2024 edition. So the result of `reader(&n)` borrows `n` as long as it's
around, wherever it goes:

```rust,error
fn reader<'a>(x: &'a i64) -> impl Fn() -> i64 with panic + Discard { move || *x }

fn main() with panic {
    let r = {
        let n = 3;
        reader(&n) // error: `n` doesn't live long enough
    };
    print(r());
}
```

For that to be sound, every region in the hidden type must be one of those
lifetimes, exactly, so that the opaque type outlives whatever all of them
do, which is what the borrow checker takes for granted of it
(`regions::type_outlives`). But the regions of a closure's type are worked
out by the borrow checker, not written, so it has to find which of the
function's lifetimes each is. It picks the least that holds everything the
region must, and is held by everything that must hold it, and then makes
the region equal to it and checks everything again. That's rustc's *member
constraints* (`borrowck::member_constraints`). The pick only decides which
programs are accepted: whatever it is, the check after it is what makes
them sound. When there's no single least one, it's an error:

```rust,error
fn either<'a, 'b>(c: bool, x: &'a i64, y: &'b i64) -> impl Fn() -> i64 with panic + Discard {
    // error: borrows for a lifetime that isn't one of `'a`, `'b` or `'static`
    let r = if c { x } else { y };
    move || *r
}

fn main() {
    print(either(true, &1, &2)());
}
```

`r` lives as long as both `x` and `y` do, which is neither `'a` nor `'b`.
With `'a: 'b` it would be `'b` (`opaque_borrow.t`).

Capturing every lifetime is simple to explain but sometimes more than
needed: `fn f(x: &i64) -> impl Fn() -> i64 with panic` ties its result to `x` even if
it only copied `*x`. Rust lets a signature list what it captures, as
`impl Fn() -> i64 with panic + use<>`; that can come later, as narrowing the list only
accepts more programs.

An opaque type is *invariant* in all its parameters: how the hidden type
uses a lifetime is part of what's hidden. A closure that writes a `&'a i64`
somewhere would let a covariant one be called with a shorter-lived
reference than it stores (`err_soundness_opaque_invariant.t`).

What its bounds say is checked with lifetimes too. A closure returning its
captured `x`, of type `&'a i64`, isn't an `impl Fn(&i64) -> &i64`, which
returns what it's given, of whatever lifetime that is; and it isn't an
`impl Fn() -> &'static i64` either (`err_soundness_opaque_static_ret.t`).

## Only what it says

An opaque type is `Discard` or `Copy` only if its bounds say so, even when
the type behind it is. So most returned closures say `+ Discard`, as
generic code says `F: Fn() + Discard` to drop an `F`. One that doesn't must
be used up, here by calling it:

```rust
fn once(b: Box<i64>) -> impl FnOnce() -> i64 with panic { move || *b }

fn main() with {alloc, panic} {
    let f = once(Box::new(4));
    print(f()); // expect: 4
}
```

Rust lets opaque types *leak* its auto traits, `Send` and `Sync`: callers
see whether the hidden type has them. That makes the body part of the
signature, so changing it can break a caller far away. Here, what a caller
can do with it is in the signature, and nowhere else.

## Running it

Monomorphisation replaces each opaque type with its hidden type, at the
type arguments it's at (`Projections::reveal`), so a copy of a function
returning one returns the closure's type, and the interpreter runs closures
as before. `t mono` shows it, as `fn adder(n: i64) -> {closure#199}`
(`opaque_fn.mono`). That
ends, as no hidden type holds its own opaque type.

## Design decisions worth noticing

- **Any bounds, not just `Fn`.** `impl Iter<Item = i64>` is the same thing,
  and iterators will want it.
- **Every lifetime is captured.** Rust's old rule captured a lifetime only
  if the bounds mentioned it, which surprised people, and its 2024 edition
  dropped it.
- **No leaking.** A caller knows what the bounds say, and that's all.
- **Equal to a lifetime, not between them.** `either` above would be sound
  if its result were known to live while both `'a` and `'b` do, but saying
  that needs intersections of lifetimes, which can come later.

## Exercises

1. Write `compose`, which takes two `Fn(i64) -> i64` and returns their
   composition. Which bounds must its type parameters have, and why?
2. Why does `t` reject `fn f() -> impl Fn() -> i64 with panic { let g = f(); move ||
   g() }`, when `fn f(n: i64) -> i64 { f(n - 1) }` is fine?
3. Make opaque types covariant in their lifetimes (`Regions::relate`), and
   run `err_soundness_opaque_invariant.t`. What goes wrong?
4. `member_constraints` picks the least lifetime that fits. Make it pick
   `'static` whenever that fits. Which tests fail, and is anything unsound?
5. A function returns `impl Show + Discard`, and its body returns an `i64`.
   Which `show` does `x.show()` call at its caller, and how does the checker
   know, if it doesn't look at the body?
6. Suppose opaque types leaked `Discard`. Write two versions of a library
   function, the second changing only its body, such that a caller that
   compiled with the first doesn't with the second.
