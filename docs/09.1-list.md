# Step 9.1: lists

Code: `alloc/list.t` (`List<T>` and its iterator, `Iter`, written in T on
top of `RawBuf`), `alloc/raw.t` (`RawBuf::empty`, the one new intrinsic),
and `src/interp.rs` (`Interp::raw_buf`, which checks what `List`'s
`unsafe` blocks promise as they run).

Since step 10 (docs/10-slices.md), `get`, `get_mut`, `iter` and `swap` go
through `as_slice` and `as_mut_slice`, which see the values in use as a
slice, and `Iter` is the slice's: what follows is how step 9.1 had them,
on `RawBuf::get` and `RawBuf::get_mut`, which a slice replaced.

```rust
use alloc::list::List;

fn main() with {alloc, panic} {
    let mut l: List<i64> = List::new();
    for i in 0..5 {
        l.push(i * i);
    }
    *l.get_mut(0).unwrap() = 100;
    let mut sum = 0;
    for x in l.iter() {
        sum = sum + *x;
    }
    print(sum);                     // expect: 130
    print(l.len());                 // expect: 5
    print_bool(l.get(5).is_none()); // expect: true
    l.free();
}
```

`List<T>` is the dense, resizable array the README promised: its values
are one after another in a buffer on the heap, `push` puts one at the end,
doubling the buffer when it's full, and `pop` takes the last one out.
`get(i)` is the value at index `i`, from `0` up to, not including,
`len()`, or `None` if there isn't one, so it can't panic, nor read memory
that holds nothing. A program says `use alloc::list::List;`, as it's not
in the prelude.

It's written in T, as `core` is, on `RawBuf<T>` from step 9
(docs/09-unsafe.md). What's new is not a rule of the checker, but how a
safe interface is made out of unsafe code.

## A safe interface over unsafe code

A `List` is a buffer and how many of its slots are in use:

```text
pub struct List<T> { buf: RawBuf<T>, len: usize }
```

The buffer doesn't know which of its slots hold values. The list does, by
its *invariant*:

> Slots `0..len` of `buf` hold values, and the rest don't, so `len <=
> buf.cap()`.

Every `unsafe` block in `alloc/list.t` counts on it, and every method
keeps it. `get(i)` checks `0 <= i < len`, so by the invariant slot `i`
holds a value, which is what `RawBuf::get` needs. `push` writes slot `len`,
which by the invariant holds nothing, after growing the buffer if `len`
was `cap()`, and then adds one to `len`, so the invariant holds again.
`pop` takes one from `len` first, and reads the slot that's no longer in
use. `swap(i, j)` reads both slots out and writes them back crossed, after
returning early when `i == j`: otherwise the second read would be of a
slot the first had emptied. Each block's `// SAFETY:` comment says which
part of the invariant it uses.

Not every method needs a block. `truncate(n)`, for a list of `Discard`
values, is `pop` until at most `n` are left, and `clear()` is
`truncate(0)`: safe code over safe methods, which can't break the
invariant, as nothing safe can.

Nothing outside `alloc::list` can break it, because the fields are
private, as an abstract type's are (docs/06d-modules.md): a program can't
write `len`, nor make a list with a literal, nor take one apart.

```rust,error
use alloc::list::List;

fn main() with {alloc, panic} {
    let mut l: List<i64> = List::new();
    l.push(1);
    l.len = 5;
    print(*l.get(4).unwrap());
    l.free();
}
// error: field `len` of `List` is private to `alloc::list`
```

So whether a program that uses a list is safe doesn't depend on that
program, only on `alloc/list.t`. That's the argument RustBelt makes for
Rust's `Vec`: an unsafe implementation is sound if every value of its type
that safe code can get hold of keeps the invariant, and every operation
safe code can call keeps it too.

Half the invariant is a refinement: `len` isn't negative, which the
checker proves at each assignment (docs/08.1-field-refinements.md). The
other half, `len <= buf.cap()`, can't be one, as a refinement can't name
what a method returns (*Deliberately missing*). It's kept by the code, and
checked as the program runs: if a method broke it, the next `unsafe` block
that counted on it would break an obligation, which the interpreter
reports.

```rust,error
use alloc::raw::RawBuf;

/// A list of our own, whose `get` is off by one.
struct Bad { buf: RawBuf<i64>, len: usize }

impl Bad {
    fn get(&self, i: usize) -> Option<&i64> {
        if i <= self.len && i < self.buf.cap() {
            // SAFETY: wrong: slot `len` isn't in use.
            unsafe { self.buf.slice(i, i + 1).get(0) }
        } else {
            Option::None
        }
    }
}

fn main() with {alloc, panic} {
    let b = Bad { buf: RawBuf::new(4), len: 0 };
    print_bool(b.get(0).is_some());
    // SAFETY: there's nothing in the buffer.
    unsafe { b.buf.free() };
}
// error: unsafe code broke its obligation: `RawBuf::slice` of slots 0..1, but slot 0 is uninitialised
```

## References into a list

`get`, `get_mut` and `iter` borrow the list, and `push` takes it `&mut`,
since it may move the values somewhere new. So the borrow checker rules
out what would read memory that's been moved, with no rule of its own:

```rust,error
use alloc::list::List;

fn main() with {alloc, panic} {
    let mut l: List<i64> = List::new();
    l.push(1);
    for x in l.iter() {
        l.push(*x);
    }
    l.free();
}
// error: cannot borrow `l` as mutable while `l` is borrowed
```

`free` takes the list by value, so nothing borrowed from it outlives its
memory either.

## Iterating

`l.iter()` is an `Iter<'_, T>`, an iterator of `&T`s, front to back. It's
`Discard`, as all it holds is a reference to the list and an index, so a
`for` loop takes it, and so do `map`, `filter`, `fold` and `count`
(docs/06e-core.md). It's safe code: `next` is `get` of the next index.

```rust
use alloc::list::List;

fn main() with {alloc, panic} {
    let mut l: List<i64> = List::new();
    for i in 1..6 {
        l.push(i);
    }
    print(l.iter().filter(|x: &&i64| **x % 2 == 0).count());      // expect: 2
    print(l.iter().map(|x: &i64| *x * 10).fold(0, |a, b| a + b)); // expect: 150
    l.free();
}
```

The loop is written `for x in l.iter()`, not `for x in &l`, which would
need `IntoIterator`; see *Deliberately missing*.

## Using a list up

A `List` isn't `Discard`, as its buffer isn't: dropping one would leak
the buffer. So it's used up, as any linear value is
(docs/06a.1-linear-types.md), by one of two methods:

- `free(self)`, when `T` is `Discard`: it throws the values away, and
  gives the buffer back;
- `free_with(self, f)`, for any `T`: it gives each value, front to back,
  to `f`, which must use it up, and then the buffer back.

```rust
use alloc::list::List;

struct Fd { n: i64 }

fn close(fd: Fd) {
    let Fd { n } = fd;
    print(n);
}

fn main() with {alloc, panic} {
    let mut l: List<Fd> = List::new();
    l.push(Fd { n: 1 });
    l.push(Fd { n: 2 });
    l.free_with(close);
    // expect: 1
    // expect: 2
}
```

`free` of a list of `Fd`s is an error, which says how to make `Fd`
`Discard`. A list of lists is used up with `free_with(|l| l.free())`.

## What a list may do

`List::new()` allocates nothing: an empty list's buffer has no slots, so
it needs no memory. That's `RawBuf::empty()`, a new intrinsic with no
effects, beside `RawBuf::new(cap)`, which has `{alloc, panic}`. So
`new`, `len`, `get`, `get_mut`, `pop`, `iter` and `free` can't allocate
or panic, and only what may grow the buffer, `push` and `with_capacity`,
says `with {alloc, panic}`:

```rust,error
use alloc::list::List;

fn empty() -> List<i64> { List::new() }

fn add(l: &mut List<i64>) { l.push(1) }

fn main() with {alloc, panic} {
    let mut l = empty();
    add(&mut l);
    l.free();
}
// error: `push` may allocate, but `add` doesn't say `with alloc`
```

`empty` needs no effects: making an empty list is as pure as making an
`Option`.

## Why it's sound

> A program that uses `List` only through its methods doesn't go wrong,
> if `alloc/list.t` keeps the invariant.

The checker trusts `RawBuf`'s intrinsics and every `unsafe` block, as in
step 9. That `List`'s blocks keep their obligations follows from the
invariant, each by the reason its `// SAFETY:` comment gives. That the
invariant holds of every `List` a program can get hold of follows from:

- **Privacy.** Only `alloc::list` can write a list's fields, make one or
  take one apart. Each of its methods keeps the invariant, given that it
  held when it was called: `new` and `with_capacity` make one with
  `len = 0`, and the rest are checked one at a time above. A function
  that took the list `&mut` and panicked halfway would leave it broken,
  but a panic aborts, so nothing sees it.
- **Borrows.** A reference from `get`, `get_mut` or `iter` borrows the
  list, so while it lives, nothing can `push` (which may move the values),
  `pop` (which may take out the one it points to) or `free` it.
- **Linearity.** A list isn't `Discard`, nor `Copy`, so its buffer is
  freed exactly once, by `free` or `free_with`, which empty it first, as
  `RawBuf::free` needs.
- **Variance.** `List<T>` is covariant in `T`, as its buffer is, which is
  sound for what owns its `T`s, as `Box<T>` is.

`free_with` hands each value to `f` before the next is read, and `f` can't
reach the list, which `free_with` owns, so the invariant can't be broken
while it runs: slots `i..len` hold values, and the rest are empty.

## Design decisions worth noticing

- **A safe interface, no new rules.** `List` needed no change to the
  checker: privacy, borrows, linearity and effects together make it safe
  to use. The one new trusted thing is `RawBuf::empty`.
- **`get` returns an `Option`.** It's total: no panic for an index out of
  range, and no refinement needed to call it. A program that knows the
  index is in range says so with `unwrap`, in its type.
- **No destructors, still.** A list is used up by a call that's written
  down. `free_with` makes that work for linear values too, so a list of
  them is as easy to use up as one of `i64`s.
- **The invariant's second half is trusted, and checked as it runs.**
  Duplicating `cap()` in a field, so that `len <= cap` could be a
  refinement, would leave `cap == buf.cap()` trusted instead, with two
  values to keep in step.

## Deliberately missing (coming later)

| Missing | Why it's missing | Step |
|---|---|---|
| `for x in &l`, `IntoIterator` | a blanket `impl<I: Iterator> IntoIterator for I` overlaps `impl IntoIterator for &List<T>`; telling them apart needs negative reasoning (`&List<T>` is never an `Iterator`), a soundness question of its own | — |
| `iter_mut` | each `&mut T` it gives must outlive the borrow of the iterator, which safe code over `RawBuf::get_mut` can't do; it needs a principled way to split a borrow | 10 ✅ |
| by-value iteration, `into_iter(self)` | the iterator would be linear, which `for` and `fold` can't use up yet; `free_with` does the same | — |
| `insert`, `remove`, `swap_remove` | each is more unsafe code to get right; they can be added when needed | — |
| `len <= buf.cap()` as a field refinement | measures: refinements that name what a method returns | — |
| freeing a list when it's dropped | destructors | — |
| strings | a list of bytes, and literals for them | — |

## Exercises

1. Write `List::swap` without an `unsafe` block, with `get_mut` twice and
   `core::mem::swap`. What does the checker say, and why? Then take the
   `i == j` check out of the real one: which test finds it, and how?
2. `truncate` is only for `Discard` values. Write `truncate_with(&mut
   self, n, f)`, which gives each value it takes out to `f`, as
   `free_with` does. Does it need an `unsafe` block?
3. Write `swap_remove(&mut self, i) -> Option<T>`, which takes the value
   at `i` out and puts the last one in its place. Which methods can it be
   written with, without a block?
4. In `push`, double the buffer when `len > cap()` instead of `len ==
   cap()`. Which obligation is broken, and which test finds it?
5. Make `List` `#[derive(Discard)]`. Which test fails first? What would a
   program that drops a list do, and why can't the interpreter's leak
   check be relied on to find it in a compiled program?
6. Write `iter_mut` for a `List<i64>` by copying `Iter`, with `get_mut`.
   What does the checker say, and why is it right to?
