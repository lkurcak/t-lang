# Step 17.1: built-ins are library items

Code: `core/mem.t`, `core/cmp.t`, `core/num.t`, `core/ops.t`,
`core/prelude.t` and `alloc/boxed.t`; the symbols in `src/traits.rs`
(`DISCARD` and the rest, `Traits::shorten`), `Checker::trait_names` and
`builtin_supertraits` in `src/check/traits/`, T-Cmp and `int_like` in
`src/check/expr.rs`, and the `Ord` calls in `src/lift.rs`.

The checker used to know nine traits by name, `Discard`, `Copy`, `Eq`,
`Int`, `Signed`, `Unsigned`, `Fn`, `FnMut` and `FnOnce`, and one type,
`Box`. They were in scope everywhere, a program couldn't use their names
for anything else, and they had no docs to show and no declaration to find.
The first retrospective (docs/17-retrospective-1.md) found that this was
the one place where a name, rather than a declaration, said what something
was. Now each is an item of a library, declared there, reached by a path,
and in scope through the prelude like `Option` is. The checker still
knows what they mean: it knows them by their paths.

## The traits are core's

Each is declared in core with `#[intrinsic]`, which says the checker gives
it impls and rules of its own, as `#[intrinsic]` on a function says the
checker gives its body:

```text
// core/mem.t
#[intrinsic]
pub trait Discard {}

#[intrinsic]
pub trait Copy: Discard {}

// core/cmp.t
#[intrinsic]
pub trait Eq {
    fn eq(&self, other: &Self) -> bool;
}

// core/num.t
#[intrinsic]
pub trait Int: Copy + Eq + Ord {}
```

`Signed` and `Unsigned` are in `core::num` too, and the `Fn` traits in
`core::ops`. The prelude brings them all in, so a program writes `Eq` as
before, and a hover shows the trait's docs. A program's own trait of the
same name is another trait: the prelude only fills in what a module
doesn't declare or import itself.

```rust
// This `Copy` is the program's: a trait with a method, nothing more.
trait Copy {
    fn copy(&self) -> i64;
}

#[derive(Discard)]
struct S { n: i64 }

impl Copy for S {
    fn copy(&self) -> i64 { self.n }
}

// Core's is still there, by its path.
fn get<T: core::mem::Copy>(x: &T) -> T { *x }

fn main(os: std::Os) -> Result<(), std::io::Error> {
    let mut out = os.stdout;
    let s = S { n: 7 };
    out.line(&s.copy())?;   // expect: 7
    out.line(&get(&3i64))?; // expect: 3
    Result::Ok(())
}
```

> **Lemma L1 (only names move).** Each of the nine traits has the
> supertraits, methods and associated types it had, and the checker gives
> it the same built-in impls and rules, now keyed by its symbol
> (`core::cmp::Eq`) rather than its name. Only core and alloc can declare
> an intrinsic, and only the nine symbols can be intrinsic traits. So no
> program can make a trait the checker treats as built in, and a
> program's `Eq`, `Discard` or `Int` gets none of what core's has: `==`
> doesn't call it, it doesn't let a value be thrown away, and it gives no
> arithmetic.

```rust,error
// A program's own `Discard` doesn't make `Fd` droppable.
trait Discard {}

struct Fd { n: i64 }

impl Discard for Fd {}

fn main() {
    let _f = Fd { n: 1 };
}
// error: `_f` is never used up, and its type, `Fd`, isn't `core::mem::Discard`
```

The rules that restrict them key on symbols too (lemma L2): `Int`,
`Signed` and `Unsigned` are sealed whatever they're imported as, and
`Discard` and `Copy` can only be derived.

```rust,error
use core::num::Int as Number;

#[derive(Discard, Copy, Eq)]
struct S {}

impl Number for S {}

fn main() {}
// error: `Int` is built in: only the integer types implement it
```

`#[derive(..)]` names its traits as any path does, by a name in scope or a
path, and only core's three can be derived:

```rust,error
trait Eq {}

#[derive(Eq)]
struct S {}

fn main() {}
// error: only `core`'s `Discard`, `Copy` and `Eq` can be derived, and `Eq` here is `crate::Eq`
```

Messages name a trait the prelude brings in by its name, `Discard`, as a
program writes it, unless the program has another trait of that name:
then by its path, as above, so the two can be told apart.

> **Lemma L4 (built-in impls keep supertraits).** If the checker gives a
> type an intrinsic trait, the type has that trait's supertraits too. For
> most it's by the same rules: every `Copy` type is `Discard`. But `Int:
> Ord`, and `Ord` isn't intrinsic: core's impls give it to each integer
> type. So when core is checked, the checker tries each built-in rule at a
> type it covers, and fails if a supertrait doesn't hold
> (`builtin_supertraits`). Without that, `T: Int` would promise an `Ord`
> that monomorphisation couldn't find.

## `Box` is alloc's

`Box` is `alloc::boxed::Box`, an intrinsic struct, and nothing of alloc's
is in the prelude, so a program that boxes says so:

```rust
use alloc::boxed::Box;

#[derive(Discard)]
enum List { Nil, Cons(i64, Box<List>) }

fn sum(l: &List) -> i64 with panic {
    match l {
        List::Nil => 0,
        List::Cons(x, rest) => *x + sum(rest),
    }
}

fn main(os: std::Os) -> Result<(), std::io::Error> with {alloc, panic} {
    let mut out = os.stdout;
    let l = List::Cons(1, Box::new(List::Cons(2, Box::new(List::Nil))));
    out.line(&sum(&l))?; // expect: 3
    Result::Ok(())
}
```

Without the `use`, `Box` is an unknown type, and the error has a fix that
adds it. The same goes for any type exactly one module of the libraries
has, `List` and `String` too.

```rust,error
fn main() with alloc {
    let _b: Box<i64> = Box::new(1);
}
// error: unknown type `Box`; import it with `use alloc::boxed::Box;`
```

> **Lemma L5 (`Box` is still a box).** A type or `Box::new` path that
> resolves to `alloc::boxed::Box` is the checker's box, `Type::Box`, as
> `Box` was: what `*b` does, moving out of a box, and that it's `Discard`
> and `Eq` when what it holds is, are all unchanged. A program's own
> `Box` is an ordinary struct, with no `*`.

## Comparisons are `Ord`'s

`==` has always been `Eq::eq(&l, &r)`, but `<` was only for integers. Now
`<`, `<=`, `>` and `>=` are `Ord`'s `lt`, `le`, `gt` and `ge`, the way
`==` is `Eq`'s:

```text
  Γ ⊢ l : T   Γ ⊢ r : T   T: Ord
 ------------------------------- (T-Cmp)     for < <= > >=
        Γ ⊢ l < r : bool
```

Like `==`, a comparison looks at its operands where they are and moves
neither. Core has `Ord` for the integers, `bool`, `char`, `str`, `&str`
and references to `Ord` values, and alloc for `String`:

```rust
use alloc::string::String;
use core::cmp::Ordering;

#[derive(Discard, Eq)]
struct Version { major: u32, minor: u32 }

impl Ord for Version {
    fn cmp(&self, other: &Version) -> Ordering {
        match self.major.cmp(&other.major) {
            Ordering::Equal => self.minor.cmp(&other.minor),
            o => o,
        }
    }
}

fn main(os: std::Os) -> Result<(), std::io::Error> with alloc {
    let mut out = os.stdout;
    out.line(&('a' < 'b'))?;     // expect: true
    out.line(&("abc" < "abd"))?; // expect: true
    let s = String::from("pear");
    let t = String::from("apple");
    let less = t < s;
    let written = out.line(&s.as_str()); // expect: pear
    s.free();
    t.free();
    written?;
    out.line(&less)?; // expect: true
    let v1 = Version { major: 1, minor: 9 };
    let v2 = Version { major: 2, minor: 0 };
    out.line(&(v1 < v2)) // expect: true
}
```

Of an integer type, `<` is still the machine's comparison: `Int: Ord`, so
a `T: Int` is ordered, and the integer types' `Ord` impls in core compare
with `<` themselves. Which one a comparison is waits until its operands'
type is known, as `|a, b| a < b` used on `i64`s shows: it's the machine's.

> **Lemma L3 (facts only from the machine's `<`).** The refinement
> checker learns `a < b` from a comparison only when it's of an integer
> type, where it's the machine's comparison, the one that runs. A program
> can't change what `<` means on integers: an impl of `Ord` for `i64`
> would be of core's trait for core's type, which only core can write,
> and `Int` is sealed, so a `T: Int` is one of the ten. A comparison of
> any other type is a call of the type's `lt`, which says nothing the
> refinement checker uses. And `lt` can't have effects: an impl's
> method can't have more than the trait's, which has none.

```rust,error
#[derive(Discard, Eq)]
struct P { x: i64 }

fn main() {
    let a = P { x: 1 };
    let b = P { x: 2 };
    let _less = a < b;
}
// error: cannot compare `P` with `<`: it doesn't implement `Ord`
```

## Design decisions worth noticing

- **The checker knows symbols, not names.** That's what makes a name a
  name: a program may use any it likes, and what core's items mean
  doesn't depend on what else is in scope.
- **`#[intrinsic]` on traits, as on functions and types.** One marker for
  "the checker supplies this", always in a library, never in a program.
- **Messages read as programs do.** The checker's errors carry exact
  symbols, and one step at the end names the prelude's traits as a
  program would, rather than each message choosing.
- **`Ord` stays a plain trait.** Its impls for the integers are written in
  core; only `<` on integers is special, so the refinement checker has a
  machine comparison to reason about.

## Deliberately missing (coming later)

| Missing | Why it's missing | Step |

| `Ord` for slices, `&[T] < &[T]` | an impl for `&[T]` next to `&T` needs the same care as `&str`'s; nothing needs it yet | — |
| `impl<T: Int> Ord for T` instead of ten impls | sealed-trait disjointness (retrospective F7) | — |
