# Step 7.1: impl parameters decided by bounds, and `where` on impls

Code: `src/traits.rs` (`impl_args`: what an impl's parameters are at a
type, and `decider`: which bound decides one the type doesn't have),
`src/check/traits/` (`Checker::collect_impls` in `collect.rs`: which
parameters an impl may have, and `Checker::bound_termination` in
`termination.rs`: which bounds an impl may need), `src/parser.rs` (`impl_decl`) and `core/iter.t` (`Map`, `Filter`).

```rust
trait Get {
    type Out;

    fn get(&self) -> Self::Out;
}

#[derive(Discard where F: Discard)]
struct Thunk<F> { f: F }

impl<U, F: Fn() -> U> Get for Thunk<F> {
    type Out = U;

    fn get(&self) -> U { (self.f)() }
}

fn main(os: std::Os) -> Result<(), std::io::Error> with panic {
    let mut out = os.stdout;
    let t = Thunk { f: || 21i64 };
    out.line(&(t.get() * 2))?; // expect: 42

    let odd_squares = (0..6i64).map(|x| x * x).filter(|x| *x % 2 == 1);
    for x in odd_squares {
        out.line(&x)?;
    }
    Result::Ok(())
    // expect: 1
    // expect: 9
    // expect: 25
}
```

Until now, each of an impl's type parameters had to be part of the type
it's for (docs/06-traits.md): finding the impl for a type then says what
each one is. `U` above isn't part of `Thunk<F>`, but it doesn't need to
be: `F`'s bound says that calling `F` gives a `U`, and `F` is part of the
type, so knowing the type is knowing `U`. At `Thunk<{closure}>` it's
`i64`, what the closure gives.

Step 7 already did this for effect parameters, with `Map`'s `f`
(docs/07-effects.md). This step does it for types, which lets `Map` and
`Filter` lose the parameters that were only there to name a type
(docs/06e-core.md).

## What decides a parameter

A parameter the type doesn't have is *decided* by an equality bound on a
parameter it does have:

- an `Fn` bound's signature, `F: Fn() -> U`, which says what `F`'s calls
  take and give;
- or an associated type's, `I: Iterator<Item = T>`, which says what
  `I::Item` is.

What the parameter is, at a type, is the part of what the bound's
projection is there, where the bound has the parameter: at `Thunk<fn() ->
Option<i64>>`, `<fn() -> Option<i64> as FnOnce>::(signature)` is `fn() ->
Option<i64>`, and `fn() -> U` has `U` where that has `Option<i64>`. Every
equality bound is still checked when the impl is used, the deciding ones
too, so `impl<U, F: Fn(U) -> U>` applies only where what `F` takes is what
it gives.

Not every place counts. One under a projection doesn't (`T::Out` doesn't
say what `T` is), nor one in effects (bounds give the most effects, and an
effect parameter its least, as in step 7). Nor does a bound on a parameter
that's only inside a function type in the impl's type, or one that's
decided itself:

```rust,error
#[derive(Discard where I: Discard)]
struct Flat<I> { iter: I }

trait Tr {
    fn go(&self) -> i64;
}

impl<T: Iterator<Item = U>, U, I: Iterator<Item = T>> Tr for Flat<I> {
    fn go(&self) -> i64 { 1 }
}
// error: type parameter `U` isn't in `Flat<I>`, nor decided by a bound
```

`T` is decided, by `I`'s bound, but `U` would be decided through `T`. That
might make sense, but it isn't needed yet, and whether working it out
always ends would need an argument of its own.

### Lifetimes a function type has of its own

A function type takes references of any lifetime: `fn(&i64) -> &i64` is
generic over its lifetime, which each call picks (docs/05-ownership.md).
So the bound's signature can have a lifetime that means nothing outside
it:

```rust,error
trait Get {
    type Out;

    fn get(&self, x: &i64) -> Self::Out;
}

#[derive(Discard where F: Discard)]
struct W<F> { f: F }

impl<T, U, F: Fn(&T) -> U> Get for W<F> {
    type Out = U;

    fn get(&self, x: &i64) -> U { (self.f)(x) }
}

fn id(x: &i64) -> &i64 { x }

fn main() {
    let f: fn(&i64) -> &i64 = id;
    let w = W { f };
    let r;
    {
        let n = 5;
        r = w.get(&n);
    }
    let _v = *r;
}
// error: `W<fn(&i64) -> &i64>` doesn't implement `Get`
```

Matching `fn(&T) -> U` with `id`'s type makes `U` a reference of the
lifetime of a call of `f`. As `Out`, that would be a reference of no
lifetime in particular, and `r` would outlive `n`. So a bound decides a
parameter only if what it decides has no lifetime of the function type
it's in; otherwise the impl doesn't apply. A function type in what it
decides is fine, lifetimes and all: those are that function type's own.

## `where` on impls

An impl can have a `where` clause, before its body, for bounds on what
isn't a type parameter:

```rust
#[derive(Discard where I: Discard)]
struct Second<I> { iter: I }

impl<I: Iterator> Iterator for Second<I> where I::Item: Discard {
    type Item = I::Item;
    effect e = I::e;

    fn next(&mut self) -> Option<I::Item> with I::e {
        match self.iter.next() {
            Option::Some(_x) => self.iter.next(),
            Option::None => Option::None,
        }
    }
}

fn main(os: std::Os) -> Result<(), std::io::Error> {
    let mut out = os.stdout;
    for x in (Second { iter: 0..6i64 }) {
        out.line(&x)?;
    }
    Result::Ok(())
    // expect: 1
    // expect: 3
    // expect: 5
}
```

`next` throws away every other value, so those must be `Discard`. Before,
an impl could only say that by naming the values' type, `impl<T: Discard,
I: Iterator<Item = T>>`, and, with `T` not part of the type, it had to be
a parameter of `Second` too: that's what `Filter<I, P, T>` did. A `where`
clause on an impl means what one on a function does. Its bounds are what
the impl needs: whoever uses it proves them, and its methods count on
them. It can bound a type parameter, decided or not, or an associated type
of one, but not `Self`, which is what the impl is about.

### Bounds that could go on forever

Proving that a type implements a trait by an impl needs what the impl
needs. When that's about parts of the type, as a bound on a type
parameter in it is, each step is about a smaller type, and the search
ends (docs/06-traits.md). A bound on `I::Item` isn't about a part:
`I::Item` can be any type, bigger ones too.

```rust,error
trait Tr {
    fn a(&self) -> i64;
}

trait Tr2 {
    fn b(&self) -> i64;
}

#[derive(Discard where I: Discard)]
struct W<I> { iter: I }

#[derive(Discard where T: Discard)]
struct V<T> { t: T }

impl<I: Iterator> Tr for W<I> where I::Item: Tr2 {
    fn a(&self) -> i64 { 1 }
}

impl<T: Tr> Tr2 for V<T> {
    fn b(&self) -> i64 { 2 }
}
// error: proving that a type implements `Tr` could go on forever
```

With an iterator `X` whose `Item` is `V<W<X>>`, proving `W<X>: Tr` needs
`V<W<X>>: Tr2`, which needs `W<X>: Tr`, which needs that again. So a bound
on what isn't part of an impl's type can only be of a trait that can't
lead back to the impl's: draw an arrow from each trait to the traits its
impls' bounds are of, and there must be no way along the arrows from the
bound's trait back to the impl's. `Filter`'s `I::Item: Discard` is fine,
as nothing `Discard` needs is ever an `Iterator`.

## Why it's sound

**Coherence.** Which impl applies to a type is still decided by its type
alone, by matching, and two impls whose types could be the same still
overlap, whatever their bounds say (docs/06-traits.md). A decided
parameter is then a function of that type: what a projection is at a type
is a function of the type (docs/06b-associated-types.md), and taking a
part of it is too. So an impl found for a type means one thing there, and
working out a projection still commutes with substitution: generic code,
the borrow checker and monomorphisation, which each work it out at a
different time, agree. In generic code, where `F` is a parameter,
`<F as FnOnce>::(signature)` is what `F`'s own bound says, so `U` is
what that says.

**Regions.** A decided parameter's regions are those of the type the impl
was found for, or of a function type inside it. The first are what an
associated type of the impl can have anyway; the second are refused, as
above.

**Termination.** Working out a decided parameter works out a projection on
a part of the impl's type, as an associated type of the impl may, and the
same rules see that it ends (`terminates`, `assoc_termination`). Proving a
bound ends, by an argument on the arrows between traits from above: group
the traits into those that can reach each other along them. Within a
group, a step of a proof is a bound on a part of the type, or on a blanket
impl's own parameter, which docs/06-traits.md shows can't go on forever.
A bound on what isn't part of the type leaves its group for one it can't
come back from, which can happen only as many times as there are groups.
So every path of a proof is finite, and as each step has finitely many
bounds to prove, the proof is.

The interpreter checks all this as it runs, as before: a value that isn't
`Discard` thrown away, because a `where` clause wasn't proved, is "type
soundness violated".

## Design decisions worth noticing

- **The type picks the impl; bounds only decide parameters.** Bounds never
  tell two impls apart, so there's still no negative reasoning, and an
  impl far away can't change which one code here uses.
- **One step from the type, for now.** A parameter decided through another
  decided one is left out, though Rust allows it: it's an extension, not a
  change.
- **The rule for `where` bounds is about traits, not types.** It's checked
  where the impls are, once, not at each use, so an impl that could loop
  is an error even if no program makes it.
- **Bounds on associated types in `<..>`, too.** `impl<T: Tr<Out: Show>>`
  means `where T::Out: Show`, so it's allowed on impls now, under the same
  rule.

## Exercises

1. Write `Zip<A, B>`, an iterator of pairs, with a decided parameter for
   each side's values. Which bounds does its impl need?
2. In `traits::impl_args`, drop the check that a decided parameter has
   no lifetime of a function type. Which test fails, and how?
3. Why must `Self` not be bounded in an impl's `where` clause? Write
   `impl<T> Tr for W<T> where Self: Tr`, and think about what proving `W<i64>:
   Tr` would then take.
4. The rule on `where` bounds refuses `I::Item: Tr2` in an impl of `Tr`
   when `Tr2` can lead back to `Tr`, even if no iterator's `Item` makes a
   loop. Find a program it refuses that would be fine. What would a rule
   that accepts it have to know?

## Reading

- Mark P. Jones, *Type Classes with Functional Dependencies* (2000): a
  parameter decided by others is a functional dependency, and an equality
  bound is one, written as a type.
- Martin Sulzmann, Gregory J. Duck, Simon Peyton Jones, Peter J. Stuckey,
  *Understanding Functional Dependencies via Constraint Handling Rules*
  (2007): the conditions under which instances with them terminate,
  Paterson's among them.
- Rust RFC 447, *No unconstrained type parameters on impls*: the rule
  this step relaxes in the same way Rust does, by "constrained by a
  projection".
