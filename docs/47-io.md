# Step 47: bytes, arguments and the environment

Code: `core/io.t` (`Read`, `Write`, `Error`, `Bytes`), `alloc/io.t`
(`read_line`, `read_to_end`, `read_to_string`), `impl io::Write for
List<u8>` in `alloc/list.t`, `std/io.t` (the streams over them),
`std/env.t` (`Args`, `Env`), the runtime in `src/cgen/hosted.h`, and the
interpreter's `Terminal` in `src/interp.rs` and `Process` in `src/lib.rs`.

Step 19 handed a program its streams (docs/19-std-io.md), and three
programs written since have each said what they're missing. tcalc can't
tell a terminal from a pipe, so it can't echo what it reads only when no
one typed it, and its tests can't see a session as a person at a
terminal would. t-nonograms wants to read a puzzle named on its command
line. And code that reads, a parser of a format, say, can only read the
one `Stdin` there is, as nothing else is a source of bytes. This is the
first of three steps that fill the `Os` in (the Os design pass): bytes,
arguments and the environment now; files next; clocks, randomness and a
raw terminal after.

## Where bytes come from, and where they go

`core::io` has two traits, of bytes as `core::fmt::Write` is of text:

```text
export trait Read {
    effect e;
    fn read(&mut self, buf: &mut [u8]) -> Result<usize, Error> with Self::e;
    fn read_exact(&mut self, buf: &mut [u8]) -> Result<(), Error> with Self::e { .. }
}

export trait Write {
    effect e;
    fn write_all(&mut self, buf: &[u8]) -> Result<(), Error> with Self::e;
    fn flush(&mut self) -> Result<(), Error> with Self::e;
    fn put<D: Display>(&mut self, x: &D) -> Result<(), Error> with Self::e { .. }
    fn line<D: Display>(&mut self, x: &D) -> Result<(), Error> with Self::e { .. }
}
```

`read` gives what's there, at most `buf.len()` bytes, and at least one
unless the input has ended, without waiting to fill `buf`: so `Ok(0)`
says the end. `write_all` writes all of `buf` or fails. What it does,
each says by its effect `e`, as `fmt::Write` does: `List<u8>`'s write
allocates, `Stdout`'s does nothing a type can see (writing is a
capability, not an effect: docs/19-std-io.md).

They're in `core`, not `std`, so code that reads and writes bytes needs
neither an operating system nor a heap: a freestanding program can be
generic over a `Read` of its serial port. In memory, `core::io::Bytes`
reads a `&[u8]` from the front, and a `List<u8>` is a `Write` onto its
end:

```rust
use alloc::list::List;
use core::io::{Bytes, Read, Write};

fn main(os: std::Os) -> Result<(), std::io::Error> with alloc {
    let mut out = os.stdout;
    let mut input = Bytes::new("abcdef".as_bytes());
    let mut buf = [0u8; 4];
    let n = input.read(buf.as_mut_slice())?;
    out.line(&n)?;                  // expect: 4
    out.line(&input.rest().len())?; // expect: 2
    let mut sink = List::<u8>::new();
    sink.put("n = ")?;
    sink.line(&n)?;
    out.line(&sink.len()) // expect: 6
}
```

Text goes into any byte sink with `put` and `line`, in UTF-8, through a
small adapter in `core::io` that's a `fmt::Write` of the sink. A blanket
`impl<W: io::Write> fmt::Write for W` would say the same, but overlap
`String`'s impl, which header unification rejects (docs/06-traits.md), so
the methods are on `io::Write` itself. `Stdout` and `Stderr` are both
kinds of sink, so they take bytes and text alike, and keep their own
`put`, `line` and `flush`, so none of these needs a `use`.

## One error for every stream

Both traits fail with the same `core::io::Error`, its kind and the
operating system's number for it, if it came from there:

```rust
use core::io::{Error, ErrorKind};

fn main(os: std::Os) -> Result<(), Error> {
    let mut out = os.stdout;
    let e = Error::os(ErrorKind::NotFound, 2);
    out.line(&e)?;                               // expect: not found (os error 2)
    out.line(&(e.kind() == ErrorKind::NotFound)) // expect: true
}
```

`fmt::Write` has an associated `Error`, so a `String`'s is `!` and its
results can be thrown away (docs/18-fmt.md). Byte streams don't, on
purpose (decision E1): `?` converts nothing (docs/15-try.md), so one type
is what lets a function read stdin, write stdout and, after the next
step, open a file, and pass every failure on with `?`. With an
associated `Error`, reading a line, which can also fail because the bytes
aren't UTF-8, would need an error type of its own, and every program
generic over its streams an enum of the two. What it costs: reading
`Bytes`, which can't fail, gives a `Result` all the same.

`std::io::Error` and `std::io::ErrorKind` are the same types, re-exported,
so programs that named them keep working.

## Lines, from anything

`alloc::io::read_line` reads a line from any `Read`, and
`Stdin::read_line` is it, without the `use`:

```rust
use alloc::io::read_line;
use alloc::string::String;
use core::io::{Bytes, Read};

fn count<R: Read>(input: &mut R) -> Result<u32, std::io::Error> with {alloc, R::e} {
    let mut line = String::new();
    let mut n = 0u32;
    while read_line(input, &mut line)? {
        n = checked_add(n, 1).unwrap_or(n);
    }
    line.discard();
    Ok(n)
}

fn main(os: std::Os) -> Result<(), std::io::Error> with alloc {
    let mut out = os.stdout;
    let mut stdin = os.stdin;
    out.line(&count(&mut Bytes::new("a\nb\r\nc".as_bytes()))?)?; // expect: 3
    out.line(&count(&mut stdin)?)                                // expect: 2
}
// stdin: one
// stdin: two
```

**Lemma R1 (a line, and no more).** `read_line` returns after reading
exactly the bytes of one line and its `\n`, if it has one: it reads one
byte at a time, and stops at the first `\n` or the end. So what `r`
gives next is the start of the next line, for every `Read`, without one
being able to give bytes back (Rust's `BufRead`). It's quick when `r`
keeps a buffer, as `Stdin` does: a byte from the buffer is a function
call, not a system call.

That's what makes a program testable without its `Os` (finding O9 of the
design pass). Tests are given no `Os` (docs/31-tests.md), but a program
generic over its streams can be given `Bytes` and a `List<u8>`, and its
test sees exactly what a person at a terminal would.

## Is anyone there?

`is_terminal()` on each stream says whether it's a terminal rather than
a file or a pipe. In a test, none is:

```rust
fn main(os: std::Os) -> Result<(), std::io::Error> {
    let mut out = os.stdout;
    let echo = !os.stdin.is_terminal();
    out.line(&echo) // expect: true
}
```

`Stdout::flush` writes out what waits in the output's buffer. The output
is written out anyway when the buffer fills, before input is read, and
when `main` returns, so a prompt before a read is seen without it.

## Arguments and the environment

The `Os` has two more fields, `args: Args` and `env: Env`:

```rust
fn main(os: std::Os) -> Result<(), std::io::Error> {
    let mut out = os.stdout;
    out.line(&os.args.program())?; // expect: t-program
    for a in os.args.iter() {
        out.line(&a)?; // expect: puzzle.txt
    }
    out.line(&os.args.get(1).is_none())?;               // expect: true
    out.line(&os.env.get("T_TEST_LANG").unwrap_or("?")) // expect: T
}
// arg: puzzle.txt
// env: T_TEST_LANG=T
```

Arguments are indexed from 0 without the program's name, which
`program()` gives apart (decision E3): `args.get(0)` is the first word
after it, and there's no `skip(1)` to forget. `Args::index(i)` needs `i`
proved less than `len()`, a measure, as a slice's does. `Env::get` reads
a variable by name; `vars()` gives them all, each a `Var { name, value }`.

`t run prog.t a b` and `t prog.t a b` pass the words after the file;
after a `--`, flags too (`t prog.t -- --verbose`), and before it, all but
`--interp`, which is `t`'s.

**Lemma A1 (process input is immutable text).** Every `&'static str`
that `Args` and `Env` give is valid UTF-8, lives until the program ends,
and never changes.

- *UTF-8.* Before `main` runs, when it takes the `Os`, the runtime checks
  each argument and variable, and if one isn't UTF-8 it says which and
  the program stops with 1 (decision D4 of the design pass). A program
  that doesn't take the `Os` can't read them, so isn't checked.
- *Lives until the end.* They're the operating system's `argv` and
  `environ` strings, which are never freed; the runtime keeps a copy of
  the array of pointers. Threads are scoped, so none outlives `main`
  (docs/41-threads.md).
- *Never changes.* Nothing in T writes them: there's no `setenv`, which
  isn't sound with threads in C. A program calling C's through `extern`
  does so in `unsafe`, whose obligation it is.

So `Args` and `Env` are `Copy`, unlike the streams: reading them changes
nothing, so it doesn't matter who reads them, or in what order (the
streams aren't `Copy` because their order matters: lemma C2 of
docs/19-std-io.md).

**Lemma C1, again (no ambient authority).** Nothing a program learns from
outside it comes but through the `Os` (or `global`, or `unsafe`). `Args`
and `Env` are intrinsic types, which no code makes (`std::env::Args {}`
is an error), so a function handed none of the `Os` is a function of its
arguments, as it was: one that reads `HOME` says so in its parameters.

```rust,error
fn home() -> Option<&'static str> {
    let env = std::env::Env {}; // error: `Env` is intrinsic: only its own functions make one or take one apart
    env.get("HOME")
}
```

## What the checker trusts

The runtime's intrinsics, private to `std`, each with what it promises:

| Intrinsic | Promise |
|---|---|
| `Stdin::os_read(buf)` | writes at most `buf.len()` bytes into `buf` and gives how many, or a failure |
| `Stdout`/`Stderr::os_write(buf)` | reads only `buf`; gives 0 or a failure |
| `os_flush`, `os_is_terminal` | touch no T memory |
| `Args::program`, `len`, `index` | the strings of lemma A1; `index(i)` for `i < len()` |
| `Env::len`, `index` | the same, of the environment |

A failure is a number with bit 63 set, the kind's place in `ErrorKind`
and the operating system's number, which one private function in
`std::io` turns into an `Error`; C maps `errno` to a kind by name
(`ENOENT`, `EACCES`, ...), the interpreter by Rust's `ErrorKind`. The
rest is T: `Bytes`, `read_exact`, the lines, UTF-8 of `put`.

## Design decisions worth noticing

- **One concrete `Error` for bytes, an associated one for text** (E1),
  for the reasons above. A sink of text is often a `String`, which can't
  fail; a stream of bytes is usually the operating system's.
- **No `BufRead` yet** (E2). Lemma R1 makes a byte-at-a-time `read_line`
  correct for every `Read`; buffering inside `Stdin`, and later a `File`,
  makes it quick. A `BufRead` trait can come when a program needs to read
  a buffered stream by more than lines.
- **`program()` apart from the arguments** (E3), unlike C and Rust.
- **`put` and `line` on `io::Write`** (E4), so a program can be generic
  over one byte sink and still write text: its test gives it a `List<u8>`.
- **`Bytes`, not `impl Read for &[u8]`**: methods are looked up on the
  type a reference points to (docs/06-traits.md), so an impl for `&[u8]`
  would be callable only as `Read::read(&mut r, ..)`.
- **The environment is checked whole, before `main`.** A variable that
  isn't UTF-8 stops a program that never reads it; reading it lazily
  would need `get` to fail, for a case that's rare.

## Deliberately missing (coming later)

| Missing | Why it's missing | Step |
|---|---|---|
| files, `os.fs` | a `File` holds an operating system resource: read ones `Discard`, written ones linear, with `close` | 48 ✅ (reading, and writing whole) |
| clocks, randomness, raw terminal mode, its size | each its own capability in the `Os` | 49 ✅ |
| `BufRead`, `BufWriter` in T | not needed yet: `Stdin` and `Stdout` buffer inside | — |
| arguments that aren't UTF-8 | a program needing them would need bytes, `&[u8]`, per argument | — |
| changing the environment | `setenv` isn't sound with threads | never |
| an exit status other than 0, 1 and 101 | `ExitCode` | — |

## Exercises

1. Write `struct Upper<W> { w: W }`, an `io::Write` that writes ASCII
   letters as capitals. What's its `e`?
2. Write a `read_line` that reads 64 bytes at a time. Find a `Read` and
   two calls where it loses bytes. What would a `BufRead` let it do
   instead?
3. Why is `Args` `Copy` but `Stdin` isn't? Would a `Copy` `Stdout` break
   lemma C2, and what about a `Copy` `Clock`?
4. `Error` is `Copy`. What would change if it carried a message, a
   `String`, as Rust's custom errors do?
5. Why is the environment checked only when `main` takes the `Os`? Show
   a program that would fail to start otherwise, for no reason it has.

## Reading

- The Rust standard library, `std::io::Read`, `Write` and `BufRead`, and
  `embedded-io`, which puts the same traits in `no_std` code, with an
  associated error type: the other choice for E1.

  MT-Unsafe, and Rust 2024's `unsafe fn std::env::set_var`, for the same
  reason: why changing the environment isn't safe with threads.
