# Step 43.1: `Debug` and format strings

Code: `Debug`, its impls, and `cat`, `display` and `debug` in
`core/fmt.t`; `Debug` for `List`, `String` and `Box` in `alloc`; the
derives in `core`, `alloc` and `std`. In the compiler, `fstring` in
`src/lexer.rs`, `ExprKind::Format` in `src/ast.rs`, `Rewrite::format` in
`src/check/modules.rs`, the `{debug}` glue in `src/mono/glue.rs`, and
the derived `fmt`'s node in `Checker::no_polymorphic_recursion`
(`src/check.rs`).

`assert_eq(&o, &Option::Some(42))` couldn't be written: `assert_eq` said
what its sides were by their `Display`, and `Display` is what a program
shows its users, which an `Option` has no one way to be. This step adds
the other way to write a value, for whoever is debugging it, and a way
to write text with values in it at all:

```rust
#[derive(Debug, Discard, Eq)]
struct Point { x: i32, y: i32 }

fn main(os: std::Os) -> Result<(), std::io::Error> {
    let mut out = os.stdout;
    let p = Point { x: 1, y: -2 };
    let name = "origin";
    out.line(&f"{name} is {p:?}, x = {p.x}")?;
    assert_eq(&Option::Some(p), &Option::Some(Point { x: 1, y: -2 }));
    Result::Ok(())
}
// expect: origin is Point { x: 1, y: -2 }, x = 1
```

Nothing there was imported: not `Debug`, nor anything `f".."` is made
of.

## `Debug`

```text
export trait Debug {
    fn fmt<W: Write>(&self, w: &mut W) -> Result<(), W::Error> with W::e;
}
```

It's `Display`'s shape (docs/18-fmt.md): the value is borrowed, the sink
is any `Write`, and writing does only what the sink does, `W::e`, and
fails only as it does. What it writes is Rust's `{:?}`: a string or
character in quotes, escaped as a literal is; a struct as its name and
fields, `Point { x: 1, y: -2 }`; a variant as its name and fields,
`Some(3)`; slices, arrays and lists as their values in brackets; a box
or reference as what it points to.

```rust
use alloc::list::List;

fn main(os: std::Os) -> Result<(), std::io::Error> with alloc {
    let mut out = os.stdout;
    let s = "say \"hi\"\n";
    let c = '\'';
    let mut l: List<Option<u8>> = List::new();
    l.push(Option::Some(1));
    l.push(Option::None);
    out.line(&f"{s:?} {c:?} {l:?}")?;
    Result::Ok(())
}
// expect: "say \"hi\"\n" '\'' [Some(1), None]
```

Only what can't be seen is escaped: the quote, `\`, tab, line break,
carriage return and nul by their escapes, the other control characters
of ASCII as `\u{..}`. Rust also escapes Unicode's invisible characters,
which needs tables of them in core: not yet.

Its method is `fmt`, as `Display`'s is. Two traits with a method of one
name make a call ambiguous where both are in scope and the type has
both, and then a path says which:

```rust
use alloc::string::String;
use core::fmt::{Debug, Display};

fn main(os: std::Os) -> Result<(), std::io::Error> with alloc {
    let mut out = os.stdout;
    let mut s = String::new();
    Debug::fmt("x", &mut s).into_ok();
    Display::fmt("x", &mut s).into_ok();
    out.line(&s)?;
    Result::Ok(())
}
// expect: "x"x
```

That's rare, as neither is in the prelude and a program seldom calls
`fmt` itself: an `f".."` does. A path like `Debug::fmt(s, w)` used to
reject `s: &str`, as `Self` would have to be `str`, which no type
variable may be. It may now, there, as it may for `s.fmt(w)`. That
gives no program an unsized value: only the libraries implement traits
for `str` and slices; their impls' methods take `Self` only by reference
(`collect_impls` checks); and no such trait has a method that gives a
`Self` without taking one by value, which no expression could pass.
(`Ord::max` takes and gives `Self`, but nothing is a `str` to pass it.)

## `#[derive(Debug)]`

A derived `Debug` writes the type's name, then each field by its own
`Debug`, as above. Like a derived `Eq`, it needs only what its fields
need (docs/06-traits.md): `struct View<'a, T> { items: &'a [T] }` is
`Debug` when `T` is. And as for every derived trait, an exported struct
with fields that aren't says that in a `where`, since its fields are no
part of its package's interface (docs/24-visibility.md):

```rust,error
#[derive(Debug)]
export struct Wrap<T> { inner: Option<T> }

fn main() {}
// error: `Wrap` is exported with fields that aren't, so its `core::fmt::Debug` must say what it needs: `where T: core::fmt::Debug`
```

Its `fmt` isn't T code: monomorphisation writes it, for each type and
sink, as MIR, as it writes a derived `==` (`{debug}::<T, W>`, see
docs/32.1-drops.md). That's because it's the same for every type but for
names, which no T function could take. So what it may do is argued
rather than checked:

> **Lemma G1 (derived `fmt`).** The body writes text with
> `W::write_str`, and each field with its type's `Debug::fmt`, which
> it borrows, with the sink reborrowed. After each, a result that
> isn't `Ok` is returned, and an `Ok` is used up. So:
> its effects are at most `W::e`, as each call's are (`Debug::fmt`'s
> are, for any impl, by the trait); it moves nothing out of the value;
> it returns the first error the sink gives, and writes nothing after
> it, so a linear `W::Error` is never dropped; and the impl each field's
> call needs exists, by the bounds worked out from the fields, as for
> `Eq`.

A type that would need copies of its `fmt` at ever bigger types is
rejected, as for `Eq`: the graph of what monomorphisation copies has a
node for each derived `fmt`, with its sink as a parameter, and an edge
for each field's `fmt` (`Checker::no_polymorphic_recursion`).

> **Lemma F4 (derive names are core's).** A bare name in
> `#[derive(..)]`, `Debug` or `Eq`, is core's trait of that name,
> whatever's in scope. A path is resolved as any path is, and must be
> to one of core's. So deriving needs no import, and a program's own
> trait called `Debug` doesn't change what `#[derive(Debug)]` means.

Before this step, `#[derive(Eq)]` named whatever `Eq` was in scope, and
was an error if that was the program's own. Nothing derivable was ever
not core's, so a bare name can only have meant core's.

## Format strings

`f"..."` is an expression: text, with *holes*. A hole names a variable,
or a field of one, `{p.x}`, and says `:?` to write it by `Debug` rather
than `Display`. `{{` and `}}` are braces; the rest is a string literal's,
escapes and all.

> **Lemma F1 (what a hole is).** A hole holds a *place*: a name, then
> fields. No calls, no operators, no blocks: nothing in it runs, so a
> format string has no effects of its own, and borrows no temporary.
> Anything else is worked out into a `let` first.

What it means is ordinary T, which the checker checks as it checks any
(`Rewrite::format`):

> **Lemma F2 (what a format string means).** Each piece is a value that's
> `Display`: text is a `&'static str`; `{x}` is `core::fmt::display(&x)`,
> which is `&x`, needing `x: Display`; `{x:?}` is `core::fmt::debug(&x)`, a
> `Dbg` holding `&x`, needing `x: Debug`, whose `Display` is `x`'s `Debug`.
> The pieces are joined by `core::fmt::cat(a, b)`, a `Cat` whose
> `Display` writes `a`, then `b`. The library's functions are named by
> their symbols, so a program's own names don't change it.

So `f"x = {p.x}, p = {p:?}"` is

```text
cat("x = ", cat(display(&p.x), cat(", p = ", debug(&p))))
```

and every property it has follows from those three functions. It borrows
each place it names, shared, for as long as it's used, so the place
can't change or move meanwhile:

```rust,error
#[derive(Debug, Discard)]
struct P { x: i32 }

fn main(os: std::Os) -> Result<(), std::io::Error> {
    let mut out = os.stdout;
    let mut p = P { x: 1 };
    let line = f"{p.x}";
    p.x = 2;
    out.line(&line)?;
    Result::Ok(())
}
// error: cannot assign to `p.x` while `p.x` is borrowed
```

Writing it does what its pieces' `fmt`s do, which is only what the sink
does (lemma F3): into a sink that can't fail, panic or allocate, it's
total. And it's a value, so it goes wherever a `Display` does:
`out.line(&f"..")?`, `String::of(&f"..")`, `panic_with(&f"..")`, a field,
another format string's hole.

> **Lemma F3 (effects).** `Cat`'s, `Dbg`'s and `&T`'s `fmt` call only
> their parts' `fmt`, with the same sink, so each does at most `W::e`;
> by induction on the pieces, so does the whole string's.

An error about a hole is at the hole, in terms of what was written:

```rust,error
#[derive(Discard)]
struct P { n: i32 }

fn main(os: std::Os) -> Result<(), std::io::Error> {
    let mut out = os.stdout;
    let p = P { n: 1 };
    out.line(&f"p = {p:?}")?;
    Result::Ok(())
}
// error: `P` doesn't implement `Debug`, which a hole `{x:?}` of a format string needs; add `#[derive(Debug)]` to `P`
```

Two bounds fail there: `debug`'s `P: Debug`, and `line`'s, that the
whole string is `Display`, which needs the same. The checker used to say
the first required; it now says the one *nearest the cause*: one that
fails itself rather than by what it needs, else one of a hole, else the
first (`Checker::prove_all`).

## `assert_eq` and `assert_ne`

They need `T: Eq + Debug`, and say both sides by their `Debug`, so a
string is quoted and a character too: `left: "abc"`. Their message is
an `f".."` in `core/panic.t`.

## Design decisions worth noticing

- **A value, not a macro.** T has no macros. A format string that's a
  value of library types needs no rule of its own: its borrows,
  lifetimes, effects and bounds are those of three small functions.
  Rust's `format_args!` is a value too, for the same reasons.
- **Places only in holes.** Rust allows only a name in an inline hole,
  `{x}`. T allows fields too, which are places, and nothing more: no
  hole can run code, so reading a format string never hides a call.
- **Glue for the derive, T for the strings.** A derived `fmt` is the
  same for every type but for names, so it's written where names are
  known, as derived `==` is; everything a program writes stays T.
- **Neither trait in the prelude.** A format string needs neither in
  scope, and `#[derive(Debug)]` needs no import, so only code that
  implements or calls `fmt` itself imports them.

## Deliberately missing (coming later)

| Missing | Why it's missing | Step |
|---|---|---|
| `{n:x}`, `{n:>8}`, `{x:#?}`: radix, width, pretty | format options need a design (wrapper types, or a `Formatter`) | — |
| `{a + b}`, `{v.len()}` in holes | holes are places; a `let` first | — |
| positional `{}` with arguments after | names say what goes where | — |
| `Debug` for `Cell`, `Mutex`, `Atomic`, iterators, closures | none is plain data; add as programs ask | — |
| escapes of Unicode's invisible characters | needs Unicode's tables in core | — |
| `Debug` for tuples | T has no tuples yet | tuples |

## Exercises

1. Write `#[derive(Debug)]`'s output for `enum E { A, B(Option<&'static
   str>) }` at `E::B(Option::Some("\t"))` without running it, then run it.
2. Why can't a hole hold `{v.len()}` without changing lemma F1? What
   would a format string that calls a method in a hole need to say about
   its effects?
3. `display` returns `&T`. Why does `{x}` borrow `x` rather than move it,
   and what would go wrong for a linear `x` if it moved?
4. Lemma G1 says the derived `fmt` uses up each `Ok` it gets. Find what
   the interpreter reports if the glue drops it instead, with a sink
   whose `Error` isn't `Discard`.
5. Design `{n:x}`: what library type would `{n:x}` mean, and which trait
   would bound `n`?
