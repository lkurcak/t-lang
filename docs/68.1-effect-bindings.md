# Step 68.1: what an associated effect may be

Code: `AssocBoundKind::Effects` in `src/ast.rs` and its parsing in
`trait_bound` (`src/parser.rs`); `preds` in `src/check/traits/bounds.rs`;
`Scheme::effect_bounds`, `ImplDef::effect_bounds` and
`OpaqueDef::effect_bounds`; in `src/check/effects.rs`
`Checker::effect_bounds_hold`, `effect_bound`, `missing_effects` and
`Why::Assoc`; and `hide` in `src/check/opaque.rs`.

`Iterator`'s `next` has an associated effect, `e`, which each impl says
(docs/07): `Range`'s is none, a `Map`'s is its closure's and its
iterator's. Code generic in an iterator could only pass `I::e` on, in its
own `with`. A function returning `impl Iterator<..>` was worse: its
caller had to say `with <impl Iterator<..> as Iterator>::e`, which can't
be written, so only a function whose effects are inferred could iterate
it (retrospective 7, L4). A bound can now say what `e` may be at most:

```rust
use alloc::list::List;

fn it<'a>(l: &'a List<u64>) -> impl Iterator<Item = &'a u64, e = {}> + Discard { l.iter() }

fn sum(l: &List<u64>) -> u64 with panic {
    let mut s = 0;
    for x in it(l) {
        s = s + *x;
    }
    s
}

fn main(os: std::Os) -> Result<(), std::io::Error> with {alloc, panic} {
    let mut out = os.stdout;
    let mut l: List<u64> = List::new();
    l.push(1);
    l.push(2);
    out.line(&sum(&l))?; // expect: 3
    Result::Ok(())
}
```

## An upper bound

`e = {alloc}` in a bound says the impl's `e` is within `{alloc}`, as a
function's `with` and an `Fn` bound's say what it may do, not what it
must. So `Range`, whose `next` does nothing, meets `I: Iterator<e =
{alloc}>`. One effect needs no braces, `e = panic`; more do, `e =
{alloc, panic}`; an effect parameter or another associated effect can
be one, `e = g`, `e = J::e`. The braces stay in what `t fmt` writes,
`e = {panic}`, as `panic` alone is read as a type, which the checker
turns into the effect when `e` is one.

Each use shows it: a call of a function with such a bound, at the
types it's called with, needs the associated effect there to be within
the set, and so does what an opaque result stands for, where the
function returns it.

```rust,error
#[derive(Discard)]
struct Down { n: u64 }

impl Iterator for Down {
    type Item = u64;
    effect e = panic;

    fn next(&mut self) -> Option<u64> with panic {
        if self.n == 0 {
            return None;
        }
        self.n = self.n - 1;
        Some(self.n)
    }
}

fn first<I: Iterator<Item = u64, e = {}> + Discard>(mut it: I) -> Option<u64> { it.next() }

fn main() {
    let _ = first(Down { n: 3 });
}
// error: `<Down as Iterator>::e` may panic, but `first` needs `I::e = {}`
```

## Rigid inside

Inside the function, `I::e` isn't `{}`, or `{alloc}`: it's still only
itself, as a type parameter is. Only where effects must be within others,
a call's within its caller's `with`, a closure's within its bound, is it
replaced by its bound. If it were equal to its bound, a function with `I:
Iterator<e = {alloc}>` could give back an allocating function as a `fn()
with I::e`, which a caller with `I = Range<u8>` would call as a `fn()`:

```rust,error
use alloc::boxed::Box;

fn allocates() with alloc {
    let _b = Box::new(1u8);
}

fn leak<I: Iterator<e = {alloc}> + Discard>(_i: I) -> fn() with I::e { allocates }

fn main() {
    let f = leak(0u8..3);
    f();
}
// error: expected `fn() -> () with I::e`, found `fn() -> () with alloc`
```

## Why it's sound

- **Lemma E1 (bounds hold where they're picked).** Every use of a
  function, a method or an opaque type with a bound `X::e = S` records
  that the associated effect, at the type arguments there, normalised, is
  within `S` (`effect_bounds_hold`, `hide`), which the effect checker
  proves as it does any other: so for each instance that runs, `X::e ⊆
  S`.
- **Lemma E2 (rigid inside).** In the body, `X::e` is only equal to
  itself, so no type with it in it is equal to one without. Where a set
  must be within another, `X::e` in the smaller one may be replaced by
  `S` (`missing_effects`): by E1, `X::e ⊆ S` at every instance, so `S ⊆
  T` gives `X::e ⊆ T`. It's never replaced in the bigger one, where `S`
  would be more than `X::e` is.
- **Lemma E3 (an opaque type's).** Outside the function, an opaque
  type's `e` is replaced by its bound the same way, with the function's
  type arguments for its parameters: what it stands for has it, by E1 at
  the return.

The effects' induction on the stack (docs/07) goes through as before: a
call's effects are within its caller's, now by E2's replacement too.

## What it doesn't do

- **An impl's bound on an associated effect** is refused: which impl a
  type has would then depend on what its effects are, which trait
  resolution doesn't look at. An impl generic in an iterator says `effect
  e = I::e;` instead.
- **Refinements in an opaque result's bindings**, `impl Iterator<Item =
  &'a mut { t: usize | t < 5 }>`, were planned with this step (L5) and
  left out. Such a refinement would be of the opaque *type*, where
  nothing the refinement checker follows can see it: a caller that gives
  the iterator to code generic in `I: Iterator<Item = &'a mut usize>`, or
  returns it as another function's opaque result, would write past it
  unchecked. Making that sound needs the checker's positions to reach
  inside opaque types: a design question of its own. Until then, return
  `IterMut<'a, { t: usize | t < 5 }>`, which says it.

## Decisions

- **An upper bound, written `e = {..}`**, as every effect bound is,
  rather than an equality, which `Range` wouldn't meet for `e = {alloc}`,
  or `e: {..}`.
- **Refinements in opaque bindings deferred** (see above): a restriction
  kept is cheaper than a hole.
- **0.83.0.** Programs that were refused are accepted.
