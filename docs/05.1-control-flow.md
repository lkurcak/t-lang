# Step 5.1: control flow, and the type with no values

Code: `src/check/expr.rs` (the typing rules, and what diverges), `src/types.rs`
(`Type::Never`), `src/borrowck/build.rs` (lowering jumps to MIR) and
`src/interp.rs` (running them).

```rust
#[derive(Discard)]
enum Option<T> { Some(T), None }

#[derive(Discard)]
enum State { Ok, Unauthorized }

fn login(user: Option<i64>) -> State {
    let id = match user {
        Option::Some(id) => id,
        Option::None => return State::Unauthorized,
    };
    if id < 0 {
        return State::Unauthorized;
    }
    State::Ok
}

fn first_square_above(n: i64) -> i64 with panic {
    let mut i = 0;
    loop {
        if i * i > n {
            break i * i;
        }
        i += 1;
    }
}

fn show(s: State) -> i64 {
    match s {
        State::Ok => 1,
        State::Unauthorized => 0,
    }
}

fn main() with panic {
    print(show(login(Option::Some(7)))); // expect: 1
    print(show(login(Option::None)));    // expect: 0
    print(first_square_above(10));       // expect: 16
}
```

`return` leaves a function early, `break` leaves a loop, `continue` goes
round it again, and `loop` loops until a `break`. They're a small step after
step 5, but they need something new in the type system: a type for an
expression that never gives a value. In `login`, one arm of the `match` is
an `i64`, and the other is `return State::Unauthorized`. What's its type?

## The type with no values

The answer is `!`, said *never*: the type with no values at all. `return e`
has type `!`, as do `break` and `continue`, because none of them ever
finish: control goes somewhere else. And since an expression of type `!`
never gives a value, it can be used as any type at all, with no danger of
giving one of the wrong type:

```text
  Γ ⊢ e : !
 ----------- (T-Never)
  Γ ⊢ e : T
```

In logic this is *ex falso quodlibet*: from a contradiction, anything
follows. `!` is the proposition with no proof, `false`, and a function
`fn absurd(n: !) -> T` is a proof that false implies anything. We've met
this type before: `enum Never {}` is one (docs/02-adts.md), and a `match`
on one needs no arms and can be any type. `!` is that type, built in, so
there's one of it that everything agrees on. A `match` with no arms is now
a `!` itself.

T-Never isn't syntax-directed: it applies to any expression whose type is
`!`, so it can't be read as a step of the algorithm the way the other rules
can. The checker uses it only where the type wanted is known
(`Checker::fits`): checking an argument against its parameter, a `let`'s
value against its annotation, a function's body against its result type.
Where two branches meet, as in an `if` or the arms of a `match`, a `!`
branch takes the type of the other (`Checker::join`). Unification never
uses it. It couldn't: unifying `!` with `i64` would have to decide which
side gives way, and the answer depends on which way values flow, which
unification doesn't know.

In a type system with subtyping, `!` is the *bottom* type, a subtype of
every type, and T-Never is just subsumption. T has no subtyping between
types (lifetimes aside), so it's a rule of its own, used in the places
where a subtype would be.

### Why a type, and not "any type"

The other way to type `return e` is to give it a fresh type variable each
time, as ML gives `raise`: it fits anywhere, because unification makes it
whatever's needed. That's what Rust did at first. The trouble is the
variable that nothing decides, as in `let x = return 1;`. A compiler has to
pick something for it, and Rust picked `()`, then spent years moving to `!`,
since the choice changes which trait implementations are picked
(rust-lang/rust#35121, and the 2024 edition's *never type fallback*).

With a type of its own, `let x = return 1;` simply makes `x` a `!`. The
variable only comes back where a `!` meets a type that isn't known yet, as
in `id(return 1)` for a generic `id<T>`: T-Never says `T` can be anything,
and nothing else says what. Then the checker picks `!`, the one choice
that's right whatever comes next (`solve_all`), so `id` is used at `id::<!>`.

There's a better reason, too. A function returning `!` promises never to
return:

```rust
fn forever() -> ! {
    loop {}
}

fn pick(c: bool) -> i64 {
    if c { 1 } else { forever() }
}

fn main() {
    print(pick(true)); // expect: 1
}
```

That's the first fact about *what a function does* that its type states,
rather than what it takes and gives. Step 7 is all about those, effects
like "may panic" or "may diverge", and a `-> !` is the simplest: "never
finishes normally". `!` is a type like any other, so it can go anywhere a
type can: an `Option<!>` is never `Some`, so a `match` on one needs no
`Some` arm (`never.t`).

## Divergence

A block with no tail is a `()`. But this function returns an `i64`, and
its body has no tail:

```rust
fn sign(n: i64) -> i64 {
    if n < 0 {
        return -1;
    }
    if n == 0 {
        return 0;
    }
    return 1;
}

fn main() {
    print(sign(-5)); // expect: -1
}
```

It's fine, as the end of the block is never reached. The checker keeps
track of whether the code it has checked so far *diverges*, never getting
to what comes next, on every path (`Checker::diverges`). A block with no
tail that diverges is a `!`, and that fits the `i64`:

```text
  Γ ⊢ { stmts } diverges
 ------------------------ (T-Block-Never)
   Γ ⊢ { stmts } : !
```

An expression of type `!` diverges. So does an `if` both of whose branches
do, and a `match` all of whose arms do. Code that may be skipped doesn't
count: the body of a `while`, which may not run, or the right side of `&&`.
And a closure's body never counts, since making a closure doesn't run it.

Why track this apart from types? Because `print(return 1)` diverges as
surely as `return 1` does, but it's a `()`: the `print` would return one,
if it were ever called. Types alone would say a block ending in that
statement can get to its end. Rust tracks divergence the same way, and for
the same reason.

Code after something that diverges never runs, so it gets a warning, as in
Rust (`unreachable_code`):

```rust
fn f() -> i64 {
    return 1;
    print(2i64);
    3
}

fn main() {
    print(f()); // expect: 1
}
// warning: unreachable code: what comes before it never finishes
```

## Loops

A `loop` runs its body again and again, and the only way out is a `break`.
So a `loop` is an expression whose value is what its `break`s give it, and
with no `break`, it's a `!`:

```text
  Γ ⊢ body : ()    the `break`s in body give T
 ---------------------------------------------- (T-Loop)
           Γ ⊢ loop { body } : T

  Γ ⊢ body : ()    no `break` in body gets out
 -------------------------------------------- (T-Loop-Never)
           Γ ⊢ loop { body } : !
```

A `while` loop can't have a `break` with a value: it can also end because
its condition is false, and then it has no value to give. It's always a
`()`. Even `while true { .. }` is, since the checker doesn't work out what
conditions are: that's a job for refinement types (step 8), if anything.

```rust,error
fn main() {
    let mut i = 0;
    while i < 10 {
        if i == 5 {
            break i;
        }
        i += 1;
    }
}
// error: a `break` with a value only works in a `loop`
```

`break` and `continue` go to the innermost loop around them. A closure's
body is a function of its own, which may be called anywhere, even after the
loop is done, so a `break` in it can't leave a loop outside it
(`err_break_closure.t`). A `return` in it returns from the closure. The
closure's result type is worked out from its `return`s, as well as its body.

### Labels

A `break` in a loop inside another leaves the inner one. To leave the
outer one, label it, `'outer:`, and say so, `break 'outer`:

```rust
fn find(n: i64, target: i64) -> i64 with panic {
    let mut i = 1;
    'outer: loop {
        let mut j = 1;
        while j < n {
            if i * j == target {
                break 'outer i * 10 + j;
            }
            j += 1;
        }
        i += 1;
    }
}

fn main() with panic {
    print(find(10, 12)); // expect: 26
}
```

`continue 'outer` goes round the outer loop again in the same way. The
`break 'outer` gives the outer `loop` its value, so it's that loop's type
that the value must fit, and the inner loop doesn't end by a `break` of its
own. Had the inner loop been a `loop`, it would be a `!`.

A label looks like a lifetime, and the lexer reads it as one, but the two
have nothing to do with each other: one names a loop, the other a region.
They don't clash, as the parser always knows which it's reading. A loop
can't have the label of a loop around it, as a `break` couldn't get to the
outer one past it (`err_label_shadowed.t`). A loop in a closure can,
though, since no `break` gets out of a closure anyway (`labels.t`). And a
label nothing names gets a warning, `unused_labels`.

Labels were one more thing the escape check of step 3 had to follow, until
step 6c retired it. It found the values a `loop` gets from its `break`s by
looking through its body, and it used to skip the bodies of loops inside
it, whose `break`s are theirs. A `break 'outer` in there is the outer
loop's, so it had to look inside too, or a closure could get out of its
frame that way.

## Jumps and memory

The borrow checker sees jumps as what they are: edges in the control-flow
graph (`build.rs`). A `return` goes to the end of the function, a `break` to
after its loop, a `continue` to its start. A jump leaves scopes on the way,
so before it, every variable and temporary in those goes away, innermost
first, just as at a block's `}` (`Builder::unwind`). Then the moves check
knows what a jump leaves behind:

```rust
fn consume(b: Box<i64>) -> i64 { *b }

fn main() with {alloc, panic} {
    let b = Box::new(5);
    loop {
        print(consume(b)); // expect: 5
        break;
    }
}
```

The box is moved inside a loop, which would be a use after a move the
second time round. But there is no second time round: the `break` is the
only way on from the move, and it leaves the loop. With `continue` in place
of `break`, it's an error (`err_move_continue.t`).

Code after a jump isn't lowered at all: control can't get to it, so it
never runs, and there's nothing to check (`Builder::reachable`). As in
rustc, dead code is type checked, and warned about, but not borrow checked
(`warn_unreachable_code.t`).

The interpreter runs a jump as a `Flow` that unwinds back up through the
expressions it's in (`interp.rs`), ending their statements and scopes on
the way, freeing what's in them, until it gets to its loop or call. One
more thing has to go: what the expressions it leaves had worked out so far.
In `f(Box::new(1), return 2)` the first argument is a box when the `return`
runs, and something has to free it. A compiled program would, and so does
the interpreter (`eval_all`), or the leak check would catch it
(`drops_jumps.t`).

And a closure that captured could leave its frame by a `return` as well as
by being the function's result, so a `return` counted as a way out for the
escape check of docs/03-inference.md, and so did a `break` that gives a
`loop` its value, if the loop was returned. (Since step 6c, the borrow
checker sees what a closure borrows, wherever it goes.)

## Design decisions worth noticing

- **`!` is a type, used through T-Never where a type is wanted, not a
  fresh type variable.** See *Why a type*.
- **`!` can go anywhere a type can**, as in `Option<!>`. Rust has
  `!` only as a function's result type on stable, after years of trying to
  stabilize the rest, mostly because of fallback.
- **A `while` loop is always a `()`.** Python's `while .. else` gives a
  `while` a value for when its condition ends it; T leaves that to `loop`
  and an `if`.
- **The unreachable code warning is for statements only**, as each block's
  first statement after something diverges, not for the rest of an
  expression like `print(return 1)`.
- **Dead code isn't borrow checked**, as it never runs. It's still type
  checked, and warned about.

## Exercises

1. Take T-Never away: make `fits` just `unify_or`. Which programs in
   `tests/t` stop checking? Which of them are wrong programs?
2. Write a block that diverges but none of whose statements' types is a
   `!`. Then make blocks diverge only if a statement is a `!`, and see
   what's rejected.
3. Rust lets a `break` with a label leave any block with that label, not
   only a loop: `'a: { if c { break 'a 1; } 2 }`. What would that take in
   the checker, the MIR builder and the interpreter? What's a labelled
   block's type, and when is it a `!`?
4. Why is `loop {}` a `!` but `while true {}` a `()`? What would it take to
   make the second a `!` too, and would it be worth it?
5. Turn off the drop in `eval_all` and run `drops_jumps.t`. What does the
   interpreter say? The borrow checker never sees `eval_all`: why does it
   agree with the interpreter on what's freed?
6. `id(return 1)` uses `id` at `id::<!>`. Make the checker pick `()`
   instead, as Rust did, and run the tests. Can you write a T program
   where the choice changes what it does? Why not, yet? (Hint: step 6.)
