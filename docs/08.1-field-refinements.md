# Step 8.1: refinements on struct fields

Code: `src/check/refine.rs` (`Checker::field_refinements`, which checks
them where the struct is declared, and the pass over each body, which now
keeps track of *places*, not just variables), `core/ops.t` (`Range::next`,
which uses its fields as they are), and `src/interp.rs`
(`Interp::check_fields`, which checks them at run time).

```rust
#[derive(Copy, Discard)]
struct Span { lo: { l: i64 | l >= 0 }, hi: { h: i64 | h >= lo } }

impl Span {
    fn len(&self) -> { n: i64 | n >= 0 } { self.hi - self.lo }

    fn shrink(&mut self) {
        if self.lo < self.hi {
            self.lo = self.lo + 1;
        }
    }
}

fn main(os: std::Os) -> Result<(), std::io::Error> {
    let mut out = os.stdout;
    let mut s = Span { lo: 2, hi: 9 };
    s.shrink();
    out.line(&s.len())?; // expect: 6
    Result::Ok(())
}
```

A field of a struct can have a refinement, as a parameter can, and it can
name the fields before it: `hi` is at least `lo`. Every `Span` keeps both:
`len` can't overflow, as `0 <= lo <= hi`, so it doesn't say `with panic`,
and promises a result that isn't negative. `shrink` adds one to `lo` only
when that keeps it at most `hi`, and the checker proves it does.

## A refinement every value keeps

A field's refinement is about the struct, not about one variable: it's
true of every value of the struct, wherever it is, in a variable, behind
a reference, in a `Box` or an `Option`, in generic code. That makes it a
rule of the type, an *invariant*, which the checker can count on whenever
it reads one: `self.hi - self.lo` above knows nothing of `self` but that
it's a `Span`.

So everything that makes or changes a `Span` must keep it:

- a literal, `Span { lo: 2, hi: 9 }`, must have every refinement, whatever
  order its fields are written in;
- assigning a field must keep every refinement that's about it: its own,
  and those of the fields after it that name it.

```rust,error
#[derive(Copy, Discard)]
struct Span { lo: i64, hi: { h: i64 | h >= lo } }

fn main() {
    let mut s = Span { lo: 1, hi: 3 };
    s.lo = 4;
    let _v = s.lo;
}
// error: can't prove `h >= lo` for field `hi` of `Span`, which names `lo`
```

Anything else that writes to a `Span` writes a whole one, which keeps them
already: `swap` of two of them, generic code, a `*r = ..` through a
`&mut Span`. What's left is a write through a `&mut` to one field, which
nothing would check, so a field a refinement is about can't be borrowed
`&mut`: not with `&mut s.hi`, nor by a method taking `&mut self`, nor by
a pattern binding it by `&mut`.

```rust,error
#[derive(Copy, Discard)]
struct Pos { n: { v: i64 | v > 0 } }

fn zero(r: &mut i64) {
    *r = 0;
}

fn main() {
    let mut p = Pos { n: 1 };
    zero(&mut p.n);
    let _v = p.n;
}
// error: can't borrow `p.n` as `&mut`: field `n` of `Pos` has a refinement, which a write through the reference could break
```

A `&mut` to the whole struct is fine, as `shrink`'s `&mut self` is.

Only an integer or `bool` field can have a refinement, and it can name only
the `i64` and `bool` fields before it, so a literal is checked in the order
the fields are declared, and no two fields' refinements are about each
other. A generic struct can have them, on its fields that are `i64`s or
`bool`s.

## Who can see a refinement

A refinement names only fields as visible as its own: a `pub` field's,
only `pub` fields; a private one's, only private ones.

```rust,error
pub struct Span { lo: i64, pub hi: { h: i64 | h >= lo } }

fn main() {}
// error: the refinement of `hi`, which is `pub`, can't name `lo`, which is private: a field's refinement can only name fields exactly as visible as it
```

Whoever can assign a field has to keep every refinement about it, so must
be able to see what they're about; and a type whose fields are private
can keep its invariant private too, as abstract types do (step 6d), so
changing it changes nothing outside.

## Facts about places

In step 8 the checker knew facts about variables. Now it knows them about
*places*: a variable, a field of a place, or what a reference or box in a
place points to. `p.x`, `self.start` (the field `start` of `*self`) and
`*b` are places. Each is a variable of the logic, as a variable was:

```rust
#[derive(Copy, Discard)]
struct P { x: i64 }

fn f(p: &P) -> i64 {
    if p.x > 0 { 10 / p.x } else { 0 }
}

fn main(os: std::Os) -> Result<(), std::io::Error> {
    let mut out = os.stdout;
    out.line(&f(&P { x: 2 }))?; // expect: 5
    let q = P { x: 4 };
    out.line(&(12 / q.x))?; // expect: 3
    Result::Ok(())
}
```

What a struct literal gives each field is known too, and goes with the
value when it's copied, or taken apart by a pattern.

Assigning a place gives it, and everything in it, a new value: after
`p = q`, what was known of `p.x` was of the old one. A loop forgets what
it assigns at the start of each time round, as before, and a branch that
assigns a place leaves it either value.

`core` uses this: `Range::next` (in `core/ops.t`) now adds one to
`self.start` only if `self.start < self.end`, with no locals to copy the
fields into, and `self.start + 1` can't overflow, as it's less than
`self.end`.

### Places lent `&mut`

A place lent `&mut` can change without an assignment the checker sees.
When it's lent to a call, and nothing can keep the reference after the
call returns, all the writes happen during the call, so it's enough to
forget what was known of it then:

```rust
#[derive(Copy, Discard)]
struct Counter { n: { v: i64 | v >= 0 }, step: { s: i64 | s > 0 } }

impl Counter {
    fn reset(&mut self) {
        self.n = 0;
    }
}

fn main(os: std::Os) -> Result<(), std::io::Error> {
    let mut out = os.stdout;
    let mut c = Counter { n: 5, step: 2 };
    c.reset();
    c.n = c.step;
    out.line(&(10 / c.n))?; // expect: 5
    Result::Ok(())
}
```

After `c.reset()`, `c.n` is a value nothing's known of but its refinement;
then it's given `c.step`, which is positive. "Nothing can keep the
reference" means the call is of a function by name, not a closure, which
could keep it between calls; and its result, what its other arguments can
write to and what's lent can't hold a reference.

Any other `&mut` to a place, kept in a variable, or lent to a call that
could keep it, makes the place one the checker knows nothing of but its
refinements, from there on: since step 21 (docs/21-measures.md), where
it's lent, as the borrow checker says nothing reads it while the borrow
lives (until then, each time it was read, in the whole body). A closure
capturing a `mut` variable, or one holding a `&mut`, still makes it so
each time it's read, in the whole body.

```rust,error
#[derive(Copy, Discard)]
struct P { x: i64 }

fn f(mut p: P) -> i64 with {} {
    if p.x > 0 {
        let r = &mut p;
        r.x = 0;
        10 / p.x
    } else {
        0
    }
}

fn main() with panic {
    let _v = f(P { x: 1 });
}
// error: `/` may panic, but `f` doesn't say `with panic`
```

A shared `&` is different: nothing can be changed through one, and what it
points to can't be changed while it can be used, so after `let r = &p.x;`,
`*r` is `p.x`.

## Why it's sound

> Every value of a struct has the refinements of its fields. Whenever the
> checker knows something of a place, it's true of the value there.

The first is an induction on how the program runs. A value of a struct is
made only by a literal, which is checked. It changes only by assigning a
field, which is checked against every refinement about the field, from
facts that are true by the second part; or by writing a whole value,
which has them already. Nothing else can write to a field a refinement is
about, since nothing can borrow it `&mut`.

The second extends step 8's. A place stands for a new variable of the
logic whenever it may change: when it, or anything it's in, is assigned;
at the start of each time round a loop that assigns it or lends it; after
a branch that does; after a call it's lent to, when the call can't keep
the reference, as every write through it is then over. Otherwise a place
lent `&mut` is a new value at every read (since step 21, from where it's
lent on, as the borrow checker says it isn't read while it's lent). A place reached through a `&`
can't change while the `&` can be used, and once it can't, nothing reads
through it again. And a struct value's fields have its refinements by the
first part.

The interpreter checks it all as it goes: every literal, every assignment
to a field, and every read of a field of a struct that has refinements,
which checks all of them. The last catches a write the checker missed
however it happened. Failing stops it with "type soundness violated".

## Design decisions worth noticing

- **A field's refinement is the type's invariant**, not a fact of a
  variable, so it survives anything that moves whole values around,
  generic code included, without that code knowing.
- **A field a refinement is about can't be borrowed `&mut`.** A `&mut`
  to the whole struct still can be, so methods can change it.
- **Same visibility**: a refinement never makes a field's assignment
  depend on what the assigner can't see.
- **Places lent to a call are forgotten after it**, but only when the
  call can't keep the reference: that holds without asking the borrow
  checker. Asking it lets every `&mut` be forgotten where it's made,
  which step 21 does.
- **No checked `Range` yet.** `Range<T>` is generic, and only `i64` and
  `bool` fields can be refined, so `start <= end` can't be its invariant.

## Exercises

1. Write `struct Ratio { num: i64, den: { d: i64 | d > 0 } }` and a
   `fn value(&self) -> i64` that doesn't say `with panic`. Why does it
   need `num` to have a refinement too?
2. Why can a `&mut Span` be lent to `swap`, but not a `&mut` to its `hi`?
   Write the program that would go wrong.
3. `Walk::borrows` checks that a call's result can't hold a reference.
   Write a program where it can, and show that forgetting the place after
   the call would be unsound... or argue that the borrow checker already
   makes it sound. Which is it?
4. Change the visibility rule to "at least as visible", and find a
   program outside a module that has to prove something about a field it
   can't see.
5. Why does the interpreter check a struct's refinements on every read of
   a field, when the checker proves them on every write?
